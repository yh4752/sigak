# 기사 본문 요약과 첫 응답 시간 개선 설계

작성: 2026-10-30 (Asia/Seoul)
상태: 2026-10-30 사용자 승인 — 일반 기사 본문 우선 구현, 논문 전문 후속.

## 목표와 유지할 계약

소개글 대신 확보한 기사 본문 전체를 한국어로 요약한다. 유료 생성은 실제 상세 방문 시에만
수행하고 결과를 방문자 간 공유한다. 기존 누적5달러 승인, 앱4달러/총200회/일20회 한도와
호출별0.02달러의 보수적 예약을 유지한다. 원장과 이미 사용한 금액을 초기화하지 않는다.

이 설계는 기존 real-ai-enrichment 설계의 입력 범위·대기 방식만 확장한다.
Spring API/작업/DB 소유, private FastAPI AI 경계, local embedding과 원본 기반 검색은 유지한다.

## 이번에 확인한 사실

- 현재 일반 기사의 입력은 RSS 소개글이며 Python 요청 전체16KiB 상한에서 앞부분을 자른다.
  따라서 본문을 확보하는 것만으로는 전체 요약이 되지 않는다.
- 작업 예약 확인과 화면 결과 확인은 각각2초 간격이다. 생성 시작·완료 표시 전 지연 요인이다.
- 이번 읽기 전용 직접 요청에서 OpenAI/Google/GitHub 원문은 모두HTTP200이었다.
  관측 응답 시간은 각각0.587/0.961/0.302초이며 일반 성능 보장 값이 아니다.
- OpenAI의 article 후보 영역은 약2.1만자였다. GitHub의 첫 article 태그는 author bio였고
  실제 본문 후보는 section.post__content였다. 범용 첫 태그 선택은 충분하지 않다.
- 시작 시 원장 관측은3회/실제 token 추정1007USDmicros/보수적 차감60000micros였다.
  이번 조사에서는 OpenAI API를 호출하지 않았다.

## 방식 비교와 권장

| 방식 | 유료 생성 시점 | 첫 방문 대기 | 추가 자원 |
| --- | --- | --- | --- |
| 신규 기사 본문만 미리 확보·저장, 요약은 클릭 시 | 실제 첫 상세 방문 | AI 생성 위주 | 읽히지 않는 기사도 제한된 HTML 요청·저장 발생 |
| 본문 수집과 요약 모두 클릭 시 | 실제 첫 상세 방문 | 원문 요청·추출과 AI 생성 | 방문한 기사만 원문 요청 |

첫 방식을 권장한다. 기사 수집 비용과 유료 AI 호출을 구분해, 읽히지 않는 기사의 AI 비용은
계속 발생하지 않게 하면서 첫 방문 때 네트워크 대기를 줄인다. 기존 기사 전체를 일괄
요약하거나 과거 본문 전체를 한꺼번에 가져오지 않는다.

## 최초 적용 범위

OpenAI Blog, Google AI Blog, GitHub Blog의 공개 HTML 기사부터 지원한다.
arXiv 논문 전문은 HTML/PDF와 긴 문서 처리가 달라 별도 후속 범위로 제안한다.
논문 초록을 기사 전문으로 표시하지 않는다. 새 본문 전용 요약 정책에서는 전문 미지원
논문에 유료 초록 요약을 자동 생성하지 않고 초록·원문 링크를 제공한다.

본문 확보 실패 시 소개글로 조용히 대체하지 않는다. 본문 요약 불가와 원문 링크를 표시한다.
접근 차단·구독 장벽·JavaScript 전용 페이지는 우회하지 않고 미지원/실패로 기록한다.

## 본문 확보·저장

- 수집은 기존처럼 바로 공개한다. 새 기사에만 무료 본문 준비 작업을 별도로 등록한다.
- 제한된 worker로 출처별 HTTP 요청과 파싱을 수행한다. AI 호출이나 유료 추출 서비스는 없다.
- 본문이 아직 없는 기존 기사는 상세 방문 시 준비 작업을 하나만 등록한다. 이미 생성한
  전문과 요약은 재사용하며, 미열람 기존 기사를 한꺼번에 재처리하지 않는다.
- 원래 소개글과 추출 전문은 별도 필드로 보존한다. 전문 상태, 확정 URL, 추출 규칙 버전,
  수집 시각, 내용 hash, 추출/요청 소요 시간과 실패 코드를 저장한다.
- 출처별 본문 root를 선택하고 메뉴·광고·작성자 소개·추천 기사·script를 제거한다.
  제목/본문 문단/후반 절의 존재 등 검증과 출처별 fixture로 잘못된 영역 선택을 막는다.
- HTTP는 승인된 출처의 HTTPS 주소만 허용하고 redirect마다 다시 확인한다. 내부/로컬
  네트워크 주소는 거부한다. 응답 크기2MiB, 요청 시간15초, redirect 최대3회로 제한한다.
  오류의 자동 반복은 제한하고 실패를 캐시해 클릭마다 같은 사이트를 재요청하지 않는다.
- 전문은 서버 내부 요약 입력으로 사용한다. 공개 API에 기사 전체를 재게시하는 변경은 아니다.

## 전문 요약 입력과 비용

전문 전체가 들어가야 FULL_TEXT로 표시한다. 광고·메뉴 제거는 입력 정리이며, 기사 중간이나
후반을 제거하는 요약 전 절단은 하지 않는다.

- 첫 버전의 전체 직렬화 요청 상한은64KiB, 출력 상한은2048token으로 제안한다.
  모델·도구·추론 모드는 기존과 같다. 다단계 분할 생성은 도입하지 않는다.
- 입력 비용은70000token을 보수적 상한으로 계산한다. 현 표준 입력$0.20/출력$1.20
  per1M 기준 최대 가정액은$0.0164576로 기존 요청별$0.02 예약 이내다.
- OpenAI Docs에 따라 explicit-only cache 모드에서 breakpoint를 만들지 않는 구성을 검증한다.
  기사별 입력은 한 번만 생성하므로 재사용되지 않는 cache write 비용을 줄이는 목적이다.
  API가 이 설정을 거부하면 별도 모델로 바꾸거나 예약을 늘리지 않고 회로를 멈춘다.
- 사용량의 cached/write token도 확인해 실제 추정 비용을 정확히 기록하고, 예상 밖 cache
  write나 사용량 초과는 추가 호출을 중단한다. 예산 검증은 paid boundary 직전에 수행한다.
- 64KiB에 전문이 들어가지 않으면 TOO_LONG으로 표시하고 AI를 호출하지 않는다.
  입력 범위를 몰래 줄여 전체 요약으로 표시하거나 여러 유료 호출로 자동 확대하지 않는다.
- 새 prompt/input 정책 버전을 사용한다. 기존 소개글 결과는 이력으로 보존하고, 사용자가
  그 기사를 다시 열었을 때에만 전문 요약을 추가 생성한다. 전체 backfill은 없다.
- current 교체는 전문 hash/버전이 같은 성공 결과에만 원자적으로 수행한다.

## 첫 응답 시간 개선

1. 본문을 미리 준비하고 HTML·광고를 제거해 클릭 후의 추가 네트워크 작업을 줄인다.
2. 요약 요청 transaction이 끝나면 worker를 즉시 깨운다. 기존 주기 실행은 복구용으로
   유지하며 coalesced 단일 실행기로 동시 요청이 중복 유료 호출을 만들지 않게 한다.
3. 화면 완료 확인 간격을2초에서0.5초로 줄이고 동일한 전체 대기 시간 안에서만 확인한다.
   GET은 읽기 전용이며, 화면이 닫히면 확인 요청을 중단한다.
4. AI 서버의 HTTP 연결을 재사용한다. timeout·재시도 금지·비용 보존 정책은 그대로다.
5. 한국어 핵심3문장/중요성1~2문장을 유지하면서 입력 범위 고지 등 화면에 이미 있는
   반복 설명을 생성문에 중복하지 않도록 prompt를 다듬는다. 근거 검증은 유지한다.

스트리밍은 후속 선택지다. 글자가 빨리 보이는 것과 전체 생성 시간이 줄어드는 것을
구분한다. 첫 버전은 검증되지 않은 부분 JSON을 표시하지 않고 검증 완료 결과를 보여준다.
전체 본문은 소개글보다 길므로 무조건 더 빨라진다고 약속하지 않는다.

## 검증과 완료 기준

- 세 출처 fixture에서 본문 앞·중간·후반, 잡음 제거, 잘못된 article root를 검사한다.
- 크기·접근 차단·미지원·긴 문서·redirect·내부 주소 거부를 유료 호출 없이 검사한다.
- 전문 준비 중 동시 클릭과 재시작, 기존 소개글 요약의 요청 시 승격, 예산 소진,
  캐시 사용량 위반·timeout을 검사한다. 이미 사용한 비용이 계속 유지되어야 한다.
- backend 전체 test/check, frontend test/lint/build, AI pytest와 실제 HTTP smoke를 실행한다.
- 최종 paid 검증은 기존 예산 안에서 소수의 실제 상세 요청만 사용한다.
  본문 fetch/추출, 큐 대기, AI 생성, 완료 표시를 분리해 관측한다. 짧아진 구간과
  전문 확대로 늘어난 구간을 모두 기록하고 실제 개선 수치만 보고한다.
