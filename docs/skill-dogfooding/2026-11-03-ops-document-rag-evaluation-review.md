## 학습형 글·독자·채용 관점

- 중심 질문은 ‘무엇이 우수한 RAG인가’가 아니라 ‘다르게 나눈 문서를 어떤 근거로 채점하는가’로 고정했다.
- 같은 명령이 두 heading에 반복되는 예로 `sourceSections`의 필요성을 설명했다. 예시는 가정임을 밝혔고 실제 장애 데이터처럼 쓰지 않았다.
- 24 intent의 48 질문을 독립 표본 48개처럼 읽지 않도록 bootstrap 단위를 설명했다.
- `NATURAL` 필드와 사람 검토 `REVIEWED`를 분리했다. 자동 검사·AI 검토를 사람 검토로 승격하지 않았다.
- 파일 역할 표와 설명 질문 6개를 남겼다. 사용자 답변이나 면접 답안을 대신 작성하지 않았다.
- 도구 도입의 이익뿐 아니라 Markdown corpus 편향, 다른 도메인·PDF로 일반화할 수 없는 비용을 기록했다.

## Humanizer 검토

40개 패턴을 여섯 범주로 수작업 검토했다. 문장부호·품사·번역투·어휘·구조 상세 참조를 읽고 해당 부분만 수정했다. 띄어쓰기 기준은 확인하되 자연스러움을 이유로 규범에 어긋나는 띄어쓰기를 만들지는 않았다. 이 기록은 편집 판단이며 통계적 AI 탐지나 저자 판별 결과가 아니다.

| 띄어쓰기 8–10 | 의존명사·보조용언·숫자 표기를 확인. 의미를 바꾸는 교정 없음 |

| 수정 전 | 수정 후 | 이유 |

초안은 대체로 자연스러웠다. 최종 자체 자연도는 A로 판단했다. 강한 상투어·hype·결론 공식은 발견하지 않았고 기술 용어는 보존했다. 이 등급은 humanizer의 편집 분류이며 객관적인 저자 판별 점수가 아니다.

근사 변경률은 약 5%다. Frontmatter·fence 코드·링크 URL을 제외한 어절 비교는 최초 윤문에서 4.2%였고, 이후 배치 공통 검사와 담당자 실행 범위를 구별하는 한 문장을 보완했다. 띄어쓰기·문장부호만의 변화는 의미 변화로 보지 않았다. 30% 미만으로 보수적으로 수정했다.

## 검증과 한계

이 담당자는 문서 읽기, 원고 작성, 보수적 윤문, 전후 비교, pinned 파일 존재 확인만 수행했다. 테스트·서비스·유료 API를 실행하지 않았다. 배치 전체의 공통 자동 검사는 root가 별도로 수행하며, 전달받은 결과는 직접 실행 결과로 바꾸지 않았다.

원고의 70 passed, 18-run, 실패 0은 2026-10-10 로그에 근거한 과거 결과다. Full multilingual 품질, reranking, 생성·judge·human calibration은 미검증/미구현으로 유지했다. 원문 존재 검사는 정답의 충분성이나 사람 검토를 대신하지 않는다.

## 스킬 평가

- 도움이 된 점: 문제·대안·구현·검증을 연결하면서 ‘준비 완료’를 ‘품질 평가 완료’로 쓰는 오류를 막았다.

- 개선 후보: 과거 검증을 인용하는 주제 글에는 ‘과거 실행 / 현재 코드 대조 / 이번 재실행’을 별도 열로 나누는 규칙을 추가하면 좋다.
