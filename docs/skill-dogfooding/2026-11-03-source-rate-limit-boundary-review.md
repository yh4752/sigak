## 독자·채용 관점 검토

- 적용 독자는 외부 RSS/API client를 운영하면서 진단·재시도·cooldown 책임을 나누려는 사람이다.
- 대안은 수동 재실행, run 전체 retry, 모든 fetch 공통 retry, host별 정책으로 비교했다.
- Clock seam을 도구 이름으로만 소개하지 않고 테스트가 실제 sleep을 없애는 방법과 보장하지 못하는 동시 실행을 설명했다.
- 429 두 번, 전송 오류 한 번이라는 기본 추가 시도 횟수와 별도 retry budget을 구별했다.
- 긴 `Retry-After`에 별도 상한 없음, 손상 timestamp가 없는 상태로 처리됨, file 수명·경로 의존을 코드에서 확인한 한계로 남겼다.
- ‘지금도 arXiv 규정을 준수하며 수집한다’는 주장은 쓰지 않았다. 외부 규칙을 새로 조회하지 않았으며 현재 외부 허용값으로 일반화하지 않았다.
- 설명 질문 6개와 다시 볼 코드 표를 만들고 답변은 작성하지 않았다.

## 검증과 한계

이 담당자는 테스트·실제 arXiv 호출·서비스 조작을 실행하지 않았다. 읽기 대조, 원고 편집, snapshot·변경률 산출, pinned blob 존재 확인을 수행했다. Root가 배치 공통 자동 검사를 별도로 진행하며 그 결과를 담당자의 직접 실행으로 기록하지 않았다.

본문의 `BUILD SUCCESSFUL`, PARTIAL 세 번, cooldown 뒤 COMPLETED는 과거 로그 인용이다. 현재 외부 규칙·가용성, 실제 다중 프로세스 경쟁, 다중 머신, 장기 운영은 미검증이다. 실제 외부 서비스를 다시 호출해 현재 상태로 승격하지 않았다.

## 스킬 평가

- 도움이 된 점: 실패 현상에서 시작해 경계·대안·검증의 간극을 순서대로 설명했다.
- 한계: 오래된 초안에는 현재와 다른 enrichment·수집 정책이 있다. 자연스러운 문장만 다듬어서는 사실 시점의 오류를 잡을 수 없어 별도 STATUS 대조가 필요했다.
- 개선 후보: 과거 장애 글 재발행 시 ‘현재 비활성/삭제/대체 여부’를 필수 확인 항목으로 두면 좋다.
