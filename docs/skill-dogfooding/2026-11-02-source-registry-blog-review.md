# 출처 등록·기사 보관 글 발행 검토

작성일: 2026-11-02
대상: `docs/blog/2026-11-02-url-source-registry-and-archive-retention.md`

## 요청과 판단 기준

사용자는 humanizer 적용 여부, 처음 읽는 개발자에게 주는 도움, 채용 관점에서 설계 판단을
확인할 수 있는지를 검토한 뒤 발행하도록 요청했다. 앞서 선택한 중심 메시지는
‘출처 변경의 편의성과 데이터 보존을 함께 설명’이다. 이 문서는 Codex가 세 관점으로
검토한 기록이며 별도의 외부 독자나 채용 담당자에게 평가를 받은 기록은 아니다.

## 내용 검토에서 고친 점

| 관점 | 원고의 약점 | 수정 |
| --- | --- | --- |
| 처음 읽는 개발자 | 운영 기록과 파일 목록이 많아 적용할 상황이 늦게 드러남 | RSS 수집기·외부 연동의 설정 변경/보관 문제를 도입부에 연결하고 YAML로 충분한 조건도 명시 |
| 설계를 평가하는 독자 | 전체 테스트 수만으로 이 변경의 보장 범위를 알기 어려움 | 설정 버전 검증, 무료 피드 본문 저장, 홈 필터/검색 순서 테스트를 실제 코드에 연결 |
| 채용 관점 | 작성자의 선택과 AI 지원 범위가 모호함 | 직접 정한 요구·보관 정책·예산 조건과 Codex의 구현·테스트/초안 지원을 구분 |
| 재현성 | 상대 `.md` 링크가 Astro 상세 URL에서 깨질 수 있음 | 11개 근거 링크를 기존 공개 Git commit의 고정 URL로 변경 |
| 사실성 | 테스트가 실제 검사하지 않는 동작까지 설명할 위험 | 기사 저장 테스트는 ‘피드 본문 저장이 유료 작업을 만들지 않음’으로 확인해 서술; 테스트 수는 전체 gate 수임을 명시 |

설계 효과를 ‘채용에 유리하다’는 문구로 주장하지 않고, 문제·대안·선택 이유·확인 가능한
코드·검증 범위가 이어지게 정리했다. 작성자의 직접 구현이나 원문 수동 검토를 새로 꾸며 넣지 않았다.

## humanizer 적용

`humanizer` v1.6.0의 40개 패턴을 문장부호·띄어쓰기·품사/명사화·어휘·구조·번역투
범주로 검토했다. 기술 식별자, 표의 명사형, 불확실성을 나타내는 필요한 가능 표현은 유지했다.
맞춤법을 일부러 틀리거나 어투를 무작위로 섞는 방법은 사용하지 않았다.

수동 편집 판단으로 원고의 S1 수정 대상은 0건, 주요 S2 수정 대상은 아래 3건이었다.
이는 AI 생성 여부를 판정하는 분류기 점수나 확률이 아니다.

| 패턴 | 전 | 후 |
| --- | --- | --- |
| 13: 정형적인 명사 중심 문장 | 보관은 저장된 요약의 재사용뿐 아니라 비용 이력을 설명할 근거를 유지하는 선택이었다 | 요약을 재사용하고 차감 내역을 추적하려면 개별 작업 기록도 남겨야 했다 |
| 33: 확인된 사실의 불필요한 가능 표현 | 기사를 지우면 연결된 요약 작업도 지워질 수 있다 | 이 스키마에서 기사를 삭제하면 연결된 작업 이력도 사라진다 |
| 21: 단락 도입의 반복적인 설명 형식 | 첫째, 출처 변경이 코드 변경이었다 / 둘째, 수집 대상을 바꿔도… | 출처 하나를 바꾸려면 Kotlin의 수집 목록을 수정해야 했다 / 수집 대상을 바꿔도… |

윤문 후 자연도는 A로 판단했다(S1 0건, 추가 수정이 필요한 S2 0건으로 수동 분류).
원문 1,811어절과 수정본 1,873어절을 비교한 근사 변경량은 478어절, 원문 대비 26.4%다.
링크 대상·코드 블록·문장부호는 계산에서 제외했다. 독자 안내와 검증 설명을 보강한 부분도
포함된 값이므로 humanizer만의 변경률은 아니다. 30% 가드 안에서 수정했다.

✓ 의미 보존 검증: 6항 모두 통과.

- 수치·날짜·고유명사: 원문 수치의 출현 수를 비교하고 기존 검증 JSON과 대조했다.
- 인과관계: 설정 변경→검증 무효, 기사 삭제→개별 작업 삭제 방향을 유지했다.
- 부정 표현: 보관·검색 허용과 신규 자동 수집 제외를 뒤집지 않았다.
- 직접 인용: 기존 따옴표 문구 4개를 그대로 유지했다.
- 핵심 주장: 등록 편의성과 데이터/비용 이력 보존을 함께 설명한다.
- 격식: 기술 블로그의 평서체를 유지했다.

## 발행·화면 검증

기존 일일 로그 7개는 frontmatter가 없어 전체 source 검사에서 실패했다. 해당 파일에
`draft: true` 메타데이터를 추가했고 원문 본문이 그대로임을 비교했다. 이번 글만 공개한다.
프로젝트 일괄 sync가 함께 가져온 이전 글 2개는 원본·복구 사본을 보존하고 이번 배포에서 제외했다.

실제로 실행한 검사:

- `npm run validate:posts -- --source --project sigak`: 30개 원본 통과.
- `npm run publish:posts -- --project sigak`: 원본·sync·발행본·테스트·빌드 전체 실행 성공.
- 요청 글만 남긴 후 `npm run validate:posts`: 34개 발행본 통과.
- 다크 모드 수정 후 `npm test`: 264개 통과, 실패/skip/cancel 0.
- `npm run build`: Astro 검사 81개 파일, 오류/경고/hint 0. 47페이지 빌드·34페이지 검색 색인과 결과 검증 성공.
- 11개 고정 근거 URL의 commit/path가 Git 객체로 존재함을 확인했고, 공개 GitHub의 해당 commit 파일 접근도 확인했다.
- CUA 실제 화면에서 데스크톱/390px 모바일, 목차 이동, 본문·표·코드를 확인했다.
  모바일 문서 폭/scroll 폭은 모두390px이었다. 긴 코드는 블록 안에서 가로 스크롤한다.

화면 검토 중 Astro가 생성한 밝은 Shiki inline 배경 위에 다크 본문 색이 표시되는 문제를
재현했다. 기존 dual theme 설정은 있었지만 다크 변수를 적용하는 CSS가 없었고,
`pre code`도 본문 글자색을 강제로 사용했다. `yonghyun-blog/src/styles/prose.css`에서
코드 색을 상속하고 선택한 다크 테마의 배경/토큰 변수를 함께 적용했다.
수정 후 plain code의 계산된 색은 다크 배경 rgb(36,41,46)/글자 rgb(225,228,232),
라이트 배경 rgb(255,255,255)/글자 rgb(36,41,46)이었다.

근거: [Astro 공식 syntax highlighting 문서](https://docs.astro.build/en/guides/syntax-highlighting/#setting-light-and-dark-mode-themes).

## 배포 직전 확인 범위

위 기록은 로컬 발행 검사·화면 확인이다. 실제 production URL과 배포 commit 확인은
배포 완료 후 같은 날짜 개발 로그에 추가한다. 이번 작성·발행 과정에서는 앱의 유료 요약이나
새 수집을 실행하지 않았으며 본문에 적힌344/70개 앱 테스트는 구현 세션의 기록이다.

스킬 적용에서 유용했던 점은 과장된 기여 서술을 피하고 의미 보존을 따로 확인한 것이다.
개선 후보는 공개 발행 전 상대 Markdown 링크와 코드 테마 대비를 함께 검사하는 절차다.
문체 검토만으로는 이 두 문제를 찾지 못했다.
