# 첫 클릭 AI 요약·비용 제어 글 검토

작성: 2026-11-02
대상: `docs/blog/2026-11-02-on-demand-ai-summary-budget.md`

## 범위와 사용자 판단

사용자는 누락 주제 감사 후 추천한 첫 번째 글을, 앞선 출처 등록 글과 같은 검토·발행
절차로 진행하도록 요청했다. 출발점은 이전 대화에서 직접 제안한 ‘읽히지 않는 기사에
미리 요약 비용을 쓰지 말고, 상세를 열 때 생성해 저장하자’는 요구다. 예산은 기존 총5달러다.
새 기여나 동기를 만들어내지 않고 이 선택을 설계의 시작으로 사용했다.

새 글 한 편이 범위다. 감사에서 발견한 리버트 원고10개나 발행 대기 글2개는 복원·발행하지 않는다.
Sigak 구현은 변경하지 않았고 실제 요약·수집 요청도 보내지 않았다.

## 코드와 기록 대조

- SummaryJobStore/ArticleSummaryService/SummaryConfig와 V4 스키마를 읽어 기사 잠금,
  입력 hash·unique key, 예산 행 잠금과 DISPATCHED 커밋, 외부 호출과 결과 저장 경계를 확인했다.
- FullTextStore와 ArticleSummary UI를 대조해 본문 준비와 유료 생성, GET과 POST,
  브라우저 이동과 서버 작업의 차이를 설명했다.
- 출력·입력 전체 제한, cache/UNKNOWN의 이전 prompt 처리도 현재 코드에 맞췄다.
  과거 설계의 앞부분 절단 제안을 현재 동작으로 옮기지 않았다.
- 2026-10-30 로그와 저장된 runtime 자료에서 Google26의 본문2293자·첫 결과11.423초,
  저장 결과0.059초·동시 완료 결과6건0.288초, GitHub46 UNKNOWN, 원문403 전송 전 중단을 확인했다.
  이 수치는 그 시점의 관측이며 이번 작성 중 다시 측정했다고 쓰지 않았다.
- 근거7개는 기존 공개 commit `a43262f944b74d81041ebfbe9746234266cf4430`으로 고정하고 Git 객체의 경로 존재를 검사했다.

## 독자·채용 관점 검토

| 검토 기준 | 반영한 내용 |
| --- | --- |
| 프로젝트를 모르는 독자도 문제를 이해하는가 | 수집 시 enrichment 후 중복을 검사하던 순서와 읽히지 않는 글의 비용 문제로 시작 |
| 왜 그 대안을 골랐는가 | 수집 시 생성·상세 진입·요약 버튼을 비교하고 첫 방문 대기를 감수한 이유를 설명 |
| 구현 판단을 확인할 수 있는가 | 요청 통합, 예산/작업 동시 기록, 네트워크 호출 동안 잠금을 놓는 순서를 분리 |
| 어려운 실패를 숨기지 않는가 | 외부 호출과 DB 저장의 원자성을 보장하지 않으며, UNKNOWN으로 가용성과 예산 활용도를 포기한 점 명시 |
| 수치로 과장하지 않는가 | DB fixture의 최초12개 동시 요청과 실서버의 완료 후6개 재요청을 구분; 지연 보장·절감률로 일반화하지 않음 |
| 작성자의 실제 역할이 보이는가 | 요구·호출 시점·예산·공유 정책 선택과 Codex의 구현/시험/글 지원을 구분 |

내용 검토 중 중복 키가 입력 변경 후 자동 재생성까지 보장하는 것처럼 읽힐 표현을 줄였다.
키는 등록된 작업의 입력을 식별하는 제약이며, 유효한 기존 결과 재사용과 재생성 정책은 별도다.
0.02달러도 실제 청구 단가가 아니라 전송 예약 시 영구 보수 차감하는 값으로 명시했다.

실제 외부 독자나 채용 담당자의 평가를 받은 것은 아니다. Codex가 위 관점으로 검토했으며,
채용 결과나 작성자의 독립 설명 능력을 검증했다고 주장하지 않는다.

## humanizer 적용과 의미 보존

40개 패턴을 문장부호·띄어쓰기·품사/명사화·어휘·구조·번역투 범주로 검토했다.
초안은 과장된 유행어와 이중 피동이 두드러지지 않아 전체를 다시 쓰지 않았다.
기술 식별자와 불확실성을 나타내는 필요한 가능 표현은 유지했다.

| 수정 전 | 수정 후 | 이유 |
| --- | --- | --- |
| 첫 클릭 때 호출한다고 중복 비용 문제가 모두 사라지는 것도 아니다 | 호출 시점을 옮긴 뒤에도 중복 비용 문제는 남았다 | 반복적인 부정 설명을 줄이고 남은 문제를 바로 제시 |
| 이 키가 모든 캐시 갱신 정책을 대신하지는 않는다 | 중복 요청 식별과 기존 결과의 재생성 정책은 별도로 뒀다 | 어떤 책임을 나눴는지 직접 설명 |
| 이 방식은 예산을 끝까지 쓰는 데 효율적이지는 않다 | 실제 사용량의 추정액이 작아도 앱의 시도 상한에 도달하면 멈춘다 | 추상적인 평가를 구체적인 동작으로 교체 |

원문1,636어절 대비 근사 변경량119어절(7.3%), 수정본1,674어절이다.
링크 대상·코드·문장부호를 제외했으며 focused 검사 수와 설명 보강도 포함한 변경량이다.
AI 탐지 확률이 아니다. 수동 자연도 평가는 A, 명확한 S1 또는 추가 수정할 S2는 없다고 판단했다.

✓ 의미 보존 검증: 6항 모두 통과.

- 수치·날짜·고유명사: 원문 수치 출현을 보존하고 새24/62개 시험 수는 실제 출력으로 확인했다.
- 인과관계: 원장 커밋→외부 호출, 응답 유실→미확정 격리 방향을 유지했다.
- 부정 표현: 미확정을 무료 실패로 바꾸거나 최초 클릭을 실제 사람 증명으로 표현하지 않았다.
- 직접 인용: 기존 따옴표 표현을 보존했다.
- 핵심 주장: 호출 시점·공유 작업·보수 예산·UNKNOWN 처리의 역할을 유지했다.
- 격식: 기술 블로그 평서체를 유지했다.
