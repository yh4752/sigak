# 2026-11-03 개발 로그: 검색 품질과 장애 대응을 나눠 평가한 이유

## 요약

사용자는 앞선 글과 같은 과정으로 다음 주제를 진행하도록 요청했다. 검색 품질과 장애 대응을
분리하는 이유를 중심 메시지로 선택했고, 기존 검색 평가 코드와 저장된 실험 자료를 대조했다.
앱 기능 변경 없이 `2026-11-03-strict-hybrid-public-search-evaluation.md`를 작성·검토·공개 발행했다.
현재 fixture와 과거 smoke를 구분하고 형식·화면·CI·공개 주소까지 확인했다.

## 오늘 완료한 일

- 후보 수집·공개 검색·내부 평가 service와 controller, Node 호출·집계·runner를 읽었다.
- `experiments/results/retrieval/latest/`의 2026-06-02 snapshot과 당시 로그·관련도 라벨을 대조했다.
- 과거 리버트된 글은 Git history에서 참고했으며 현재 코드·근거로 새 날짜의 글을 작성했다.
  다른 리버트 원고는 복원하지 않았다.
- 실패한 HYBRID와 정상 반환된 PUBLIC의 의미, macro/effective의 분모, 대체 경로 사용을 설명했다.
- 최초 초안에 humanizer를 적용하고 독자·채용 관점의 검토 기록을
  `docs/skill-dogfooding/2026-11-03-search-evaluation-blog-review.md`에 남겼다.

## 설계 고민 / 결정

독자가 검색 응답 성공을 두 경로의 결합 품질로 오해하지 않도록, 장애 예시와 선택지부터 설명했다.
시험용 임베딩·작은 표본의 수치를 현재 의미 검색 성능으로 일반화하지 않았다. 실패 분모를
설명하는 두 건의 가상 실행도 실제 집계 함수로 계산하고 운영 관측과 구분했다.

코드 대조 중 지연 측정은 내부 후보 재사용과 공개 왕복 시간을 섞는다는 점을 확인했다.
과거 표의 HYBRID 평균15ms를 속도 우위로 인용하지 않았다. 공개 last-search 지표 경합·
지표 누락 시 degraded=false 집계·HTTP 실패 시 배치 중단도 글에 명시했다.

## 트레이드오프

이번 범위는 검증·기술 글 한 편이다. 공개 평가 도구의 실패 수집이나 지연 측정을 수정하지 않았다.
현재 fixture가 보장하는 동작과 향후 운영 측정의 차이를 글의 일부로 남겼다.
사용자가 선택한 글의 강조점과 Codex의 구현·시험·작성 지원을 구분했다.
