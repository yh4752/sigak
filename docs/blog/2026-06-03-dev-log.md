# 2026-06-03 개발 로그: arXiv 수집 429 rate limit 대응

## 요약

오늘은 dataset/search evaluation 확장 중 발견된 arXiv collection `429 Too Many Requests`
실패를 backend 수집 fetch 경계에서 다뤘다. 기존에는 429를 `TRANSIENT_FETCH`,
`retryable=true`로 분류만 했고, 실제 retry나 throttle은 없었다.

이번 세션에서는 `export.arxiv.org` 요청만 최소 3초 간격으로 직렬화하고, 429 응답은
`Retry-After` 우선 backoff로 제한 재시도하도록 구현했다. 이후 실제 runtime smoke에서
`arxiv-cs-cl` read timeout과 반복 smoke 후 429가 재현되어, arXiv 전용 transient fetch
retry와 source HTTP read timeout 기본값 30초도 추가했다.

RSS/Atom 일반 source의 retry 정책, Neo4j 작업, article detail API, dataset/search
evaluation artifact는 건드리지 않았다. GitHub issue는 먼저 생성해 #14로 추적했고,
runtime smoke가 아직 `PARTIAL`이라 close하지 않았다.

## 오늘 완료한 일

- `backend/src/main/kotlin/com/sigak/collection/service/SourceCollectionService.kt`
  - `HttpSourceContentFetcher`에 arXiv export host 전용 fetch 경로를 추가했다.
  - arXiv 요청은 lock으로 단일 연결처럼 직렬화하고, 요청 시작 시각 기준 최소 간격을 둔다.
  - HTTP 429는 `Retry-After` seconds 또는 HTTP-date 값을 우선 사용하고, 없으면 기본 delay를 사용한다.
  - arXiv read timeout 같은 `ResourceAccessException`도 별도 지연 후 제한 재시도한다.
- `backend/src/main/kotlin/com/sigak/collection/config/CollectionHttpConfig.kt`
  - `ArxivFetchProperties`를 추가했다.
  - source HTTP read timeout 기본값을 10초에서 30초로 올렸다.
  - 테스트 가능한 `Clock`, `SourceFetchDelay` 경계를 운영 bean으로 연결했다.
- `backend/src/main/resources/application.yml`, `backend/src/test/resources/application.yml`, `.env.example`
  - arXiv 정책 설정값을 `SIGAK_COLLECTION_ARXIV_*` 환경 변수로 노출했다.
- `backend/src/test/kotlin/com/sigak/collection/service/HttpSourceContentFetcherTest.kt`
  - arXiv 연속 요청 throttle, non-arXiv bypass, 429 `Retry-After` retry, retry limit, read timeout retry 테스트를 추가했다.
- `backend/src/test/kotlin/com/sigak/collection/config/CollectionHttpPropertiesTest.kt`
  - source HTTP 기본 timeout과 arXiv 설정 binding을 검증했다.
- `docs/superpowers/specs/2026-06-03-arxiv-rate-limit-design.md`
- `docs/superpowers/plans/2026-06-03-arxiv-rate-limit.md`
- `docs/STATUS.md`
  - arXiv rate-limit handling과 이번 검증 결과를 기록했다.

## 설계 고민 / 결정

해결 위치는 `CollectionRunService`나 source registry가 아니라 `HttpSourceContentFetcher`로 잡았다.
문제는 특정 source의 parse/persist가 아니라 `export.arxiv.org` HTTP 호출 정책이었기 때문이다.
이렇게 두면 controller, command runner, collection service의 공개 계약은 그대로 두고, 내부 fetch
행동만 보강할 수 있다.

모든 source에 retry를 일반화하지 않고 arXiv host에만 적용했다. RSS feed의 4xx/5xx까지 한 번에
정책화하면 실패 의미가 섞이고, MVP 범위를 넘어서는 scheduler/queue 설계로 번질 수 있다. 이번에는
공식 arXiv 제한에 맞춘 최소 정책만 넣었다.

## 트레이드오프

얻은 것:

- 5개 source를 연속 수집할 때 arXiv source 간 요청이 3초보다 촘촘해지지 않는다.
- 429가 와도 즉시 source 실패로 끝나지 않고, `Retry-After`가 있으면 그 값을 따른다.
- arXiv read timeout은 한 번 더 시도할 수 있다.
- fake clock/delay로 실제 sleep 없이 정책을 테스트할 수 있다.

미룬 것:

- 전체 collection retry queue/scheduler는 아직 없다.
- 실제 arXiv 서버를 대상으로 한 collection-run smoke는 실행했지만 아직 `PARTIAL`이다.
- 같은 관리 머신에서 다른 프로세스나 반복 command-run이 arXiv를 호출하는 상황까지 전역으로 조율하지는 않는다.

## 다음 단계

- #14는 닫지 않는다. 충분한 cooldown 후 runtime smoke를 한 번만 다시 실행하거나,
  반복 command-run까지 고려한 local cross-process throttle/cooldown guard를 별도 설계한다.
- collection failure diagnostics에서 arXiv 429 재발 여부를 계속 확인한다.
- source별 정책이 더 늘어나면 fetcher 내부 조건문을 별도 policy/decorator로 분리할지 검토한다.
- general retry queue/scheduler는 full run history 설계와 함께 별도 작업으로 다룬다.
