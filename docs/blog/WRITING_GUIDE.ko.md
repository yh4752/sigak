# Codex용 Dev-log 작성 지시문

이 문서는 **구현을 마친 Codex(코딩 에이전트)가 그 세션의 dev-log를 작성할 때 따르는 규칙**이다.

dev-log의 목적은 세 가지다.

1. 매일 무엇을 개발했는지 기록한다. (성실성)
2. 블로그에 그대로 올려 진행 과정을 공개한다.
3. 나중에 기술 블로그 주제를 고를 때 참고할 **근거 저장소**가 된다.

따라서 dev-log는 "잘 쓴 글"보다 **정확하고, 일관되고, 나중에 검색 가능한 기록**이 우선이다.

---

## 가장 중요한 규칙: 세션에서 실제로 일어난 것만 쓴다

Codex는 자기가 방금 한 구현 세션의 컨텍스트(바뀐 파일, 실제로 실행한 명령, 그 출력)를 가지고 있다. dev-log는 그 컨텍스트에서만 사실을 가져온다.

- **실제로 실행한 명령과 그 실제 출력만** 검증 근거로 적는다. 명령을 상상해서 적지 않는다.
- 테스트/스모크를 **돌리지 않았으면** "통과"라고 쓰지 않는다. `미검증` 또는 `다음 세션에서 검증 예정`이라고 명시한다.
- 숫자(count, latency, 통과 테스트 수 등)는 **실제 출력에서 본 값만** 쓴다. 그럴듯한 값을 지어내지 않는다.
- 구현하지 못하고 미룬 것은 "완료"가 아니라 **"준비"** 또는 **"미완"** 으로 구분한다.
- 불확실하면 단정하지 말고 불확실하다고 적는다. 과장보다 누락이 낫다.

> 이 규칙을 어긴 dev-log는 나중에 주제 참고용으로 쓸 때 잘못된 근거가 되어 더 해롭다.

---

## 고정 구조

파일명: `YYYY-MM-DD-dev-log.md` (실제 작업일)

```md
# YYYY-MM-DD 개발 로그: (오늘의 핵심 주제 한 줄)

## 요약
오늘 한 일의 핵심과 그 이유를 3~5줄. "무엇을, 왜, 어디까지" 했는지.

## 오늘 완료한 일
실제로 끝낸 작업. 각 항목에 관련 파일 경로를 적는다. 안 끝난 건 여기 쓰지 않는다.

## 설계 고민 / 결정
왜 이 구조를 택했는가. (한 일 나열이 아니라 "왜"를 적는다)

## 트레이드오프
얻은 것 / 미루거나 포기한 것. "완성"과 "준비"를 구분.

## 검증
실제로 실행한 명령 + 실제 결과. 안 한 것은 미검증으로 표기.
| 영역 | 실행한 명령 | 결과 |

## 다음 단계
이어서 할 일. 미완으로 남긴 것 포함.

## 블로그 주제 후보 (topic-queue 반영)
아래 "주제 후보 평가"를 거쳐 등록할 후보가 있으면 여기 요약하고 topic-queue.md에 추가.
```

작업 성격에 따라 `설계 고민`과 `트레이드오프`는 합쳐도 되지만, **"왜 이렇게 했는가"는 반드시 한 번 이상** 드러나야 한다. 단순 작업 나열로 끝내지 않는다.

---

## 작성 후 자가 점검 (Codex가 스스로 확인)

dev-log를 끝내기 전 아래를 통과해야 한다.

- [ ] 모든 검증 결과가 이번 세션에서 **실제로 실행한** 명령의 결과다.
- [ ] 돌리지 않은 테스트를 "통과"라고 쓰지 않았다.
- [ ] 지어낸 숫자가 없다.
- [ ] "완료한 일"에 미완 작업이 섞여있지 않다.
- [ ] "왜 이렇게 했는가"가 최소 한 곳에 설명돼 있다.
- [ ] 관련 파일 경로가 실제 존재하는 경로다.
- [ ] 주제 후보 평가를 거쳐 topic-queue를 갱신했다.

---

## 주제 후보 평가 (나중 블로그 주제 선정용)

dev-log를 쓴 뒤, 이번 세션이 블로그 주제 후보 조건에 맞는지 평가한다. **아래 중 2개 이상** 해당하면 `topic-queue.md`에 후보를 추가한다.

- 새로운 기술/라이브러리/저장소/인프라 도구를 도입했다.
- 대안이 있었고, 선택하지 않은 이유를 설명할 수 있다.
- 의도적으로 MVP 이후로 미룬 일이 있다.
- 실패, 장애, fallback, rebuild, retry, 복구 전략을 다뤘다.
- 성능, latency, count, success/failure 같은 metric을 남겼다.
- public/internal API, service/repository 같은 경계를 나눴다.
- 테스트, smoke check, 운영 명령으로 검증한 결과가 있다.
- 면접에서 "왜 이렇게 설계했나요?"를 받을 만하다.

중복 처리:

1. `topic-queue.md`에 비슷한 후보가 이미 있으면 새로 만들지 말고 **관련 파일·검증 근거·핵심 질문만 보강**한다.
2. 없으면 새 후보를 추가한다.

후보 형식(기존 topic-queue.md와 동일):

```md
## [candidate] 주제명
- 날짜: YYYY-MM-DD
- 관련 작업:
- 관련 파일:
- 감지 이유:
- 글의 핵심 질문:
- 검증 근거:   (이번 세션에서 실제로 실행한 명령과 결과)
- 추천 글 유형:
- 상태: candidate
```

## Codex에게 줄 프롬프트 (구현 세션 끝에 붙여 사용)

구현을 끝낸 Codex에게 아래를 그대로 지시한다.

```text
방금 끝낸 구현 세션을 기준으로 dev-log를 작성해라.
규칙은 docs/blog/WRITING_GUIDE.ko.md를 따른다. 특히:

1. 이번 세션에서 네가 실제로 바꾼 파일과 실제로 실행한 명령/출력만 근거로 써라.
   - 실행하지 않은 명령, 보지 않은 숫자, 안 돌린 테스트 결과를 만들어내지 마라.
   - 검증하지 않은 것은 "미검증"으로 명시해라.
2. 파일은 docs/blog/YYYY-MM-DD-dev-log.md (오늘 날짜)로 만들어라.
3. 고정 구조(요약 / 완료한 일 / 설계 고민·결정 / 트레이드오프 / 검증 / 다음 단계 /
   블로그 주제 후보)를 따라라.
4. 단순 작업 나열로 끝내지 말고, 핵심 결정에 대해 "왜 그렇게 했는가"를 설명해라.
5. 완료한 일과 미룬 일을 구분해라. ("완성"과 "준비"를 섞지 마라)
6. 작성 후 "주제 후보 평가"를 수행해라. 조건 2개 이상이면 docs/blog/topic-queue.md를
   갱신해라. 비슷한 후보가 있으면 새로 만들지 말고 보강해라.
7. 끝내기 전 자가 점검 체크리스트를 통과시켜라.

마지막에, 검증한 것과 미검증으로 남긴 것을 따로 요약해서 나에게 보고해라.
```

이 프롬프트의 핵심은, Codex가 "글을 그럴듯하게 쓰는 것"이 아니라 **세션의 사실을 정확히 기록하고 + 나중에 쓸 주제를 큐에 적립**하도록 강제하는 것이다.

## 주제별 강조 포인트 (dev-log·주제 선정 공통 참고)

해당 영역을 건드린 세션이면, dev-log의 "설계 고민"과 topic-queue "핵심 질문"에 아래를 우선 반영한다.

- **Backend**: controller를 얇게 유지하고 service에 business logic을 둔 이유 / DTO와 entity 분리 / transaction, lazy loading, N+1, repository query 설계 / 외부 client 호출 실패 처리 / 테스트 가능한 service boundary.
- **Search·RAG**: PostgreSQL source of truth와 ES/Qdrant/Neo4j projection store 분리 / indexing, rebuild, fallback, alias, bulk API / keyword·vector·hybrid의 역할 차이 / retrieval quality 비교용 query set과 metric / Graph RAG를 제품 기능과 평가 실험으로 구분.
- **AI Server**: FastAPI를 AI/RAG 전용 boundary로 둔 이유 / mock mode 유지 이유와 real provider 교체 경계 / prompt, schema validation, unsupported claim, evidence coverage / 유료 API 없이 local development 유지.
- **Frontend**: API client boundary에서 Zod 검증 이유 / loading·error·empty state 설계 / 검색 상태·URL·detail navigation·related fetch 흐름 / 복잡한 state 관리 라이브러리 미도입 이유.
- **Infra·Deploy**: Docker Compose 우선 이유 / cloud-specific dependency를 MVP 이후로 미룬 이유 / AWS 배포 시 비용·teardown·secret·network boundary / local reproduction과 demo deployment의 역할 차이.

---

## 나중에 주제형 기술 블로그를 쓸 때

dev-log와 topic-queue가 쌓이면, `ready-to-write` 후보를 골라 **별도의 주제형 기술 블로그**를 쓴다. dev-log와 달리 시간순이 아니라 **문제→결정→트레이드오프→결과** 구조로 한 주제만 깊게 다룬다. (예: `2026-05-28-flyway-adoption.md`)

```txt
매일: 구현 -> Codex가 dev-log 작성 + topic-queue 적립
가끔: topic-queue에서 ready-to-write 선택 -> 주제형 기술 블로그 1편 작성
```

주제형 글 구조:

```md
# (문제·결과 중심 제목 — 날짜 금지)
> 한 줄 요약: 무엇을 / 왜 / 어떤 결과로

## 배경과 문제
## 선택지와 결정   (대안 비교는 표로)
## 구현            (핵심 코드/흐름, ASCII 다이어그램)
## 트레이드오프     (얻은 것 / 미룬 것)
## 결과와 검증      (재현 가능한 명령 + 측정값을 상단으로)
## 다음 단계
```

주제형 글에서도 dev-log의 "세션에서 검증한 사실만 쓴다" 원칙은 동일하게 적용한다. 단, 근거는 topic-queue에 적립된 검증 명령/결과에서 가져온다.
