# 2026-05-07 개발 로그: Mock MVP에서 서비스화와 연구 포트폴리오 구조로 확장

## 요약

지난 2026-05-05 개발 로그에서는 Sigak의 제품 방향을 정리하고, mock data 기반의 첫 MVP 흐름을 만들었다. 당시의 핵심은 "중요한 기술 변화를 맥락과 관계와 함께 설명하는 서비스"라는 제품 정의, Spring Boot + FastAPI + React 구조, 기사 목록/검색/상세 화면, 그리고 프론트엔드 상태 처리였다.

그 이후 작업의 중심은 한 단계 더 실제 서비스에 가까운 구조로 옮겨갔다. mock article API만으로 제품의 모양을 증명하는 단계에서, PostgreSQL 기반 영속성, 수집과 enrichment foundation, 연구형 포트폴리오 전략, 그리고 문서 체계 정리까지 진행했다.

이번 작업의 가장 큰 변화는 Sigak을 단순한 뉴스 요약 데모가 아니라, 다음 두 층을 가진 프로젝트로 재정의한 것이다.

```txt
실제로 사용할 수 있는 기술 뉴스 인사이트 서비스
+ LLM/RAG 실험 결과를 제품 안에서 보여주는 Research Dashboard
```

즉, 서비스와 연구를 따로 보여주는 것이 아니라, 실제 뉴스 데이터 파이프라인 위에서 나온 검색/RAG/Graph-aware/fine-tuning 실험 결과를 `/research` 같은 별도 페이지에서 시각화하는 방향으로 잡았다.

## 2026-05-05 이후 진행한 일

### 1. PostgreSQL 기반 영속성 MVP 도입

5월 5일에는 article data가 mock data 중심이었다. 이후에는 PostgreSQL과 JPA 기반의 persisted article 구조를 추가해, 백엔드가 실제 저장소를 source of truth로 사용할 수 있는 기반을 만들었다.

진행한 내용은 다음과 같다.

- PostgreSQL Docker Compose 구성
- Flyway 기반 schema 구성
- JPA entity와 repository 구성
- persisted article list/detail/search API 연결
- curated seed article data 구성
- raw article content와 enrichment 결과를 분리하는 모델 방향 반영
- Testcontainers 기반 PostgreSQL integration test 구성

이 변화의 의미는 크다. 이제 Sigak은 "화면에 보이는 mock card"가 아니라, 수집된 원문과 AI enrichment 결과를 보존하고 재처리할 수 있는 구조로 넘어갈 수 있다. 특히 나중에 semantic search, Graph RAG, fine-tuning dataset export를 하려면 원본 텍스트와 enrichment output을 분리해서 저장하는 것이 중요하다.

### 2. Collection과 LLM Enrichment Foundation 정리

자동 수집은 아직 완성된 end-to-end pipeline은 아니지만, 수집과 enrichment가 어떤 경계로 움직여야 하는지는 꽤 구체화했다.

완료된 기반은 다음과 같다.

- source registry 구성
- RSS/Atom collector boundary 구현
- arXiv collector boundary 구현
- collected article model 구성
- article normalizer 구현
- mock enrichment client 구현
- collector, normalizer, pipeline service tests 작성
- internal enrichment contract 문서화

중요한 결정은 broad open-web crawling을 하지 않는다는 것이다. Sigak은 양보다 질이 중요한 서비스이기 때문에, 초기 수집은 명시적인 source registry에서 시작한다. 공식 발표, 연구 source, 주요 릴리즈, 보안 advisory처럼 신뢰할 수 있는 출처를 먼저 다루고, Hacker News 같은 커뮤니티 aggregator는 초기 원본 source에서 제외했다.

처리 흐름은 다음 방향으로 정리했다.

```txt
DISCOVER
-> FETCH
-> EXTRACT
-> NORMALIZE
-> ENRICH_WITH_LLM
-> REVIEW_OR_PUBLISH
-> INDEX
```

아직 남은 핵심은 이 기반을 실제 persistence writer와 연결하는 것이다. 즉, source에서 가져온 article이 normalize되고, mock 또는 real enrichment를 거쳐 DB에 저장되고, `/api/articles`와 frontend에 나타나는 흐름을 완성해야 한다.

### 3. FastAPI AI 서버의 위치를 명확히 함

현재 FastAPI 서버는 mock enrichment endpoint를 제공한다.

```http
POST /api/enrichment/article
```

지금 단계에서는 OpenAI API key가 없어도 로컬 개발이 가능해야 하므로 mock mode를 유지한다. 다만 최종본에서는 다음과 같은 mode를 둘 수 있도록 방향을 잡았다.

```txt
AI_ENRICHMENT_MODE=mock
AI_ENRICHMENT_MODE=openai
AI_ENRICHMENT_MODE=local
```

여기서 중요한 점은 "AI agent를 먼저 만드는 것"이 아니라, 구조화된 enrichment call을 먼저 안정화하는 것이다. summary, why-it-matters, topics, category, importance candidate처럼 명확한 output schema가 있는 기능은 agent보다 일반 LLM call과 validation으로 시작하는 편이 더 안전하다.

Agentic workflow는 나중에 여러 article을 비교하거나, retrieval tool을 호출하거나, failure case를 분석하는 연구/운영 기능에서 검토하는 것이 더 자연스럽다.

### 4. 코드 리뷰를 통해 현재 리스크를 정리

현재 구조에서 바로 고쳐야 할 리스크도 정리했다.

첫 번째는 backend article API filtering이다. 현재 `getArticles()` 흐름은 모든 article을 response graph로 변환한 뒤 query filter를 적용하는 구조라, 앞으로 `DISCOVERED`, `FAILED`, enrichment 미완료 article이 DB에 들어오면 검색과 무관한 row 때문에 500 오류가 날 수 있다. public API에는 `PUBLISHED`이고 current enrichment가 있는 article만 노출되도록 repository 또는 service query 단계에서 제한해야 한다.

두 번째는 frontend article detail의 related article stale state다. 관련 기사가 있는 article에서 없는 article로 이동할 때 이전 related list가 남을 수 있으므로, article 변경 시 `relatedArticles`를 먼저 비우고 stale fetch result를 막아야 한다.

세 번째는 FastAPI enrichment schema validation이다. `Field(min_length=1)`은 whitespace-only string을 허용하므로, 실제 AI 연동 전 input boundary에서 stripped string validation과 `suggestedImportanceScore`의 0-100 범위 검증을 추가해야 한다.

이 리스크들은 큰 기능이 아니지만, 다음 단계인 collection-to-persistence 연결 전에 반드시 정리해야 하는 안정화 작업이다.

## 연구 포트폴리오 방향 정리

### 1. LLM/NLP 연구실 제출을 위한 방향

Sigak을 LLM/NLP 연구실에도 제출할 수 있는 포트폴리오로 만들기 위해, 단순히 "LLM을 사용했다"가 아니라 "무엇을 비교했고, 어떤 기준으로 평가했는가"가 드러나야 한다고 판단했다.

그래서 연구 포트폴리오의 논지를 다음처럼 잡았다.

> Sigak은 기술 뉴스 수집, 검색, 요약, 관계 기반 인사이트를 하나의 서비스로 제공하고, 그 과정에서 retrieval, RAG, graph-aware context, fine-tuning이 실제로 품질을 개선하는지 재현 가능한 실험으로 평가한다.

핵심은 기능명보다 평가다. RAG, GraphRAG, fine-tuning 같은 단어를 붙이는 것보다 baseline, metric, failure case, cost, latency를 함께 보여주는 것이 더 설득력 있다.

### 2. 논문 기반 개발 트랙

연구 전략 문서에서는 유명 논문과 방법론을 Sigak 안에서 어떻게 활용할지 정리했다.

주요 트랙은 다음과 같다.

- RAG track: no-RAG vs retrieved-context RAG 비교
- Retrieval evaluation track: keyword/BM25, dense retrieval, hybrid retrieval 비교
- Self-RAG-inspired track: 생성 결과의 unsupported claim이나 evidence coverage 점검
- GraphRAG-inspired track: concept와 article relation을 이용한 graph-aware insight 실험
- Fine-tuning track: event type/category/importance bucket classification에서 zero-shot, few-shot, LoRA/QLoRA 비교

여기서 fine-tuning은 생성형 요약 모델을 무리하게 학습시키는 방향이 아니라, 작은 classification task부터 시작하는 것이 좋다고 판단했다. 예를 들어 article의 `eventType`이나 `primaryCategory`를 분류하는 task는 label을 만들기 쉽고, zero-shot/few-shot/fine-tuned baseline을 비교하기 좋다.

### 3. Research Dashboard 방향

문서나 README에만 연구 결과를 적는 것보다, 실제 서비스 안에 연구 결과를 보여주는 페이지를 두는 것이 더 강한 포트폴리오가 될 수 있다고 봤다.

초기 route는 다음처럼 단순하게 시작한다.

```txt
/research
```

처음에는 하나의 페이지 안에서 다음 섹션을 보여주고, 데이터가 커지면 하위 route로 나눈다.

- Overview
- Retrieval Benchmark
- RAG Evaluation
- Graph-Aware Insight
- Fine-Tuning
- Failure Analysis

Research Dashboard는 장식용 차트가 아니어야 한다. 보여주는 데이터는 `experiments/results/*.json`, PostgreSQL에 저장된 article/enrichment/relation metadata, retrieval/RAG/fine-tuning 평가 결과에서 나와야 한다.

## 문서 구조 정리

문서가 늘어나면서 `docs` 루트에 roadmap, research roadmap, master roadmap, status report, product plan, project context가 함께 놓이게 되었다. 내용 자체는 가치가 있었지만, 처음 보는 사람이 어떤 문서를 먼저 읽어야 하는지 알기 어려웠다.

그래서 문서 구조를 다음처럼 정리했다.

```txt
docs/
├── README.md
├── PRODUCT.md
├── ROADMAP.md
├── RESEARCH_STRATEGY.md
├── STATUS.md
├── API_SPEC.md
├── SOURCE_POLICY.md
├── ko/
│   └── GUIDE.md
├── decisions/
├── blog/
└── superpowers/
```

정리 기준은 세 가지였다.

첫째, 포트폴리오 독자가 바로 읽어야 하는 문서를 루트에 남긴다. `PRODUCT.md`, `ROADMAP.md`, `STATUS.md`, `API_SPEC.md`, `RESEARCH_STRATEGY.md`가 그 역할을 한다.

둘째, 역사 기록은 유지한다. ADR, blog, superpowers specs/plans는 개발 과정의 흔적이므로 지우지 않고 그대로 둔다.

셋째, 살아있는 문서를 명확히 한다. `STATUS.md`는 현재 상태와 리스크를 업데이트하는 문서이고, `ROADMAP.md`는 앞으로의 실행 순서와 phase를 관리하는 문서다.

이 정리로 `docs`는 단순한 파일 모음이 아니라, 읽는 순서가 있는 정보 구조가 되었다.

## 주요 결정과 트레이드오프

### Mock에서 Persistence로 넘어간 이유

초기에는 mock data가 맞았다. API 계약과 UI 흐름을 빠르게 검증할 수 있었기 때문이다. 하지만 collection, enrichment, search, Graph RAG를 이야기하려면 결국 원문과 AI output을 저장해야 한다.

그래서 PostgreSQL persistence를 도입했다. 다만 Elasticsearch와 Qdrant는 아직 미뤘다. 검색 인덱스와 vector store는 데이터와 baseline이 충분히 쌓였을 때 붙이는 편이 낫다.

### Research Dashboard를 서비스 안에 두기로 한 이유

연구 결과를 README 표로만 보여주면 프로젝트와 연구가 분리되어 보일 수 있다. 반대로 서비스 안에 `/research` 페이지를 두면, Sigak의 AI 기능이 어떻게 평가되고 개선되는지 제품 경험 안에서 설명할 수 있다.

다만 Research Dashboard가 서비스보다 먼저 커지면 안 된다. 뉴스 목록, 검색, 상세, 수집, enrichment가 먼저 안정화되어야 dashboard가 의미를 가진다.

### Fine-tuning은 나중에, 하지만 실험으로 준비

Fine-tuning은 할 수 있지만, 지금 당장 생성형 요약 모델을 학습시키는 것은 과하다. 데이터셋과 baseline이 없는 fine-tuning은 포트폴리오에서 오히려 설득력이 떨어질 수 있다.

그래서 순서는 다음이 맞다.

```txt
dataset
-> zero-shot baseline
-> few-shot baseline
-> LoRA/QLoRA fine-tuning
-> evaluation
```

작은 classification task부터 시작하면 연구실 관점에서도 실험 설계가 더 명확해진다.

### 문서를 줄이는 것이 아니라 읽는 경로를 만든 이유

문서가 많다는 것 자체가 문제는 아니었다. 문제는 역할이 겹치는 문서가 같은 위치에 있어서, 어디서부터 읽어야 할지 모호했다는 점이다.

그래서 무작정 삭제하지 않고, 중복 내용을 대표 문서에 통합했다. 제품은 `PRODUCT.md`, 실행 순서는 `ROADMAP.md`, 현재 상태는 `STATUS.md`, 연구 방향은 `RESEARCH_STRATEGY.md`로 나눴다.
