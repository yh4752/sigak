# 2026-11-02 개발 로그: URL로 출처를 등록하기 위한 설계

## 요약

사용자는 출처를 추가할 때 코드 수정 없이 URL을 등록하는 구조를 원했다.
기존 수집 registry·출처 저장·본문 처리 코드를 읽고 PostgreSQL을 운영 출처 정본으로
쓰는 설계 초안과 제안 상태의 ADR을 작성했다. 세 블로그의 공개 피드 형식을 무료로
확인했다. 기능 구현과 배포, 실제 수집 대상 변경은 이번 작업에 포함하지 않았다.

## 설계 고민 / 결정

`SourceRegistry`의 고정 목록과 DB `news_sources`가 따로 존재했다. 저장 과정에서는
표시 이름의 영문 slug로 출처를 찾고 새 레코드 URL에 기사 주소를 넣을 수 있었다.
URL 설정만 옮기면 이중 관리와 한글 이름 충돌이 남으므로 고정 source ID를 수집부터
저장까지 전달하고 DB registry로 통합하도록 설계했다.

RSS에는 `content:encoded`가 남지만 본문 저장소로 연결되지 않고, Atom은 `summary`만
읽고 있었다. 피드의 실제 content를 보존하면 추가 페이지 요청을 줄일 여지가 있다.
다만 긴 필드가 전문이라고 보장할 수 없으므로 원문 표본 대조 후 사용하는 정책을 제안했다.
요약 생성 시간 자체가 얼마나 줄어드는지는 측정하지 않았다.

## 트레이드오프

DB 등록은 YAML보다 이관·상태 관리가 필요하지만 재배포 없이 출처를 관리할 수 있다.
처음에는 운영 명령만 만들고 관리자 화면·인증·공개 등록 API는 미룬다.
기계 검사는 본문 최소 조건을 확인하고 운영자는 활성화 전에 표본을 확인한다.
범용 크롤러, 논문 전문, AI 기사 선별, 커리어 전용 category/prompt는 범위에서 제외했다.
기존 첫 클릭 요약과 누적 예산 이력을 보존하는 것이 제약이며 새 비용은 발생시키지 않았다.

## 검증

| 영역 | 실제 실행/확인 | 결과 |
| --- | --- | --- |
| 현재 코드 | `SourceRegistry`, 출처 entity/repository, 수집·저장 service, RSS/Atom parser, 본문 fetch/store/worker, Flyway, Caddy 읽기 | 코드 고정 registry, 이름 기반 key, Atom content 누락, 고정 본문 host를 확인 |
| 공개 피드 | `python3` stdin에서 urllib·ElementTree·HTMLParser로 토스 루트/피드·우아한형제들 피드·D2 피드를 각1회 읽기 | HTTP200, 토스20개·우아한형제들10개·D2 20개; 각 첫3개에 본문 content 필드 존재, 토스 루트의 RSS alternate 확인 |
| 피드 크기 | 위 응답 실제 읽은 bytes | 토스704270, 우아한형제들306859, D2 1018389; 모두2MiB 이하 |
| 근거 검증 | `.venv/bin/python -m rag_evaluation validate-dataset --allow-draft` | 첫 실행은 tokenizer 정의 DNS 실패. 네트워크 허용 재실행에서 evidenceValidated=true, reviewed0, fullEvaluationReady=false, fixed48/heading84 |
| 검토 자료 | `.venv/bin/python -m rag_evaluation prepare-review --output datasets/review.md` | 60개 query, reviewed0으로 갱신 |
| 설계 자가 검토 | 모순·placeholder·범위 검토 | 입력 제한, 전문 확인 기록, 기존 출처 이관 예외와 오류 처리 범위를 구체화 |
| 문서 정합성 | Python으로 변경 문서8개의 로컬 링크·공백·code fence 검사, `git diff --check` | 로컬 링크16개 확인, 오류0, diff 공백 오류 없음 |

검증 명령의 실행 위치는 RAG 두 명령만 `experiments/rag-evaluation`이며 나머지는
저장소 루트다. 호스트 Python의 일반 공개 HTTP 확인은 실제 배포 JVM이나 새 fetcher의
안전성 검증이 아니다. 전문 완전성·요약 품질·운영 상태·잔액/누적 카운터는 미검증이다.
backend/frontend/AI 코드는 변경하지 않아 해당 테스트는 실행하지 않았다.

## 다음 단계

설계 초안을 사용자와 검토한 뒤 구현 계획을 작성한다. DB 이관·고정 ID, 공통 외부 요청,
등록·검증, 본문 재사용 순으로 구현하고 마지막에 배포 환경의 세 출처 표본을 검증한다.
기존 출처 중단과 신규 후보 활성화는 아직 실행하지 않았다.
