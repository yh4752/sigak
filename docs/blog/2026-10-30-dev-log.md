# 2026-10-30 개발 로그: 실제 접속 복구와 단일 서버 배포 준비

## 요약

오래 중지된 Sigak 서비스를 다시 시작하고 오늘 기준 전체 검사를 실행했다.
이전 개발 내용이 로컬에만 남아 있음을 확인하고 GitHub와의 차이를 구분했다.

## 설계 고민 / 결정

정적 Sites-only 배포는 기존 JVM backend를 실행할 수 없으므로 실제 기사 검색 서비스의 대체가 되지 않는다. 기존 Spring Boot public boundary와 PostgreSQL 원본을 유지하고 한 서버의 Compose에 Caddy만 공개하기로 했다.

SPA는 알 수 없는 경로에도 index.html을 반환하므로 API 제한이 fallback보다 먼저 실행돼야 한다. 정확한 공개 API와 GET/HEAD만 proxy하고 내부·unknown API에는 404, API 쓰기 method에는 405를 반환한다. 실제 HTTP 검사에서 이 경계를 확인했다.

기존 개발 DB와 새 배포 DB를 분리했다. 배포 설정 실험이 수집 기사 41개를 덮어쓰지 않도록 새 DB는 샘플 5개로 검증하고 기존 데이터는 보존했다. 연구 artifact의 catalog 41개는 API가 읽는 보존 artifact의 크기이며 새 배포 DB의 기사 수와 구분한다.

## 트레이드오프

- 서버 한 대로 운영 구성을 단순화했지만 HA나 자동 backup/scheduler는 포함하지 않는다.
- 임시 HTTPS 공유는 검증했지만 서버나 도메인이 없어 상시 인터넷 서비스와 사용자 도메인 TLS는 미검증이다. 유료 자원 생성이나 결제는 하지 않았다.
- JDK Alpine tag의 ARM manifest 부재를 실제 빌드에서 확인해 Jammy 기반으로 교체했다. 이미지 크기보다 현재 ARM/향후 서버 호환성을 우선했다.
- Host의 기존 node_modules로는 발견되지 않던 peer lock 누락을 Linux clean install로 찾았다. 설치 우회 대신 lock을 보완하고 같은 빌드를 다시 실행했다.
- 평가 테스트의 초기 19개 실패는 sandbox DNS/tokenizer 다운로드 문제였다. 네트워크 허용 후 같은 70개가 통과했으며 코드 오류로 기록하지 않는다.
- Dataset 사람 검토는 여전히 0개다. 생성·judge·전체 품질 평가 gate를 변경하지 않았다.

## 후속 작업: Sigak 기술 뉴스 정기 수집

### 사용자 선택과 구현 범위

사용자는 news-rag의 경향신문 수집 데이터를 옮기는 대신 Sigak의 기술 뉴스 source를 자동 실행하도록 선택했다. 별도 news-rag 컨테이너·코드·데이터는 변경하지 않았다. 기존 개발 DB 41개는 실제 수집 36개와 seed 5개였고, 마지막 실제 수집은 한국시간 6월5일이었다는 DB 감사도 수행했다. 기존 news-rag worker의 600초 반복·최근 성공은 별도로 확인했으며 두 프로젝트를 혼동해 보고하지 않도록 구분했다.

구현 파일: collection config의 `CollectionAutomationProperties/Config`, service의 `CollectionAutomationService`, dto의 `CollectionAutomationStatus`, runner의 `CollectionAutomationScheduledJob`, controller의 `CollectionAutomationController`, 관련 automation test3개 파일. `application.yml`, root/deployment env example, deployment Compose와 backend Dockerfile, 내부 API 계약·배포 안내·상태/로드맵을 갱신했다.

### 이유와 트레이드오프

- 별도 scheduler나 Airflow를 새로 도입하지 않고 기존 Spring backend에 opt-in fixed-delay job을 연결했다. 개발/test는 꺼 두고 배포만 기본 활성화한다.
- 완료 후 대기와 in-process guard로 예약 실행 중복을 막는다. 한 backend만 지원하며 replica 간 분산 잠금과 수동 작업 동시 실행은 지원하지 않는다.
- 신규 저장 뒤 projection이 실패해도 PostgreSQL은 보존한다. 다음 실행이나 재시작에서 새 기사가 없어도 복구한다. 수집 도중 일부가 저장된 뒤 예외가 난 경우도 pending으로 남기는 회귀 테스트를 RED→GREEN으로 검증했다.
- 각 저장소 갱신 실패를 격리하고 정제된 오류 타입만 남긴다. `lastSuccessfulAt`와 `lastPublishedAt`를 구분해 일부 실패를 성공처럼 보고하지 않는다.
- 진단 snapshot은 메모리 상태이고 재시작 시 초기화된다. 실제 기사/실패 이벤트/volume cooldown만 영속적이다. 전체 run history나 가동률 계산은 구현하지 않았다.
- 기존 mock enrichment와 bounded feed batch, 전체 projection rebuild를 유지한다. 유료 LLM, 과거 전체 backfill, 대규모 증분 색인은 추가하지 않았다.

- 브라우저에서 신규 OpenAI 기사(한국시간10월30일 발행)의 실제 제목·날짜·원문 링크·요약 표시를 확인했다. 화면을 `outputs/deployment-2026-10-30/automatic-news-article.jpg`에 보존했다. 요약/why-it-matters는 기존 mock 결과이며 외부 유료 생성 품질을 검증한 것이 아니다.

## 후속 설계: 누적 5달러 이내 실제 AI 기사 요약

### 요약과 완료한 일

사용자가 실제 AI 요약을 요청하고 기존 OpenAI 잔액 약 5달러 이내 사용을 선택했다.
이번 후속 세션에서는 코드·배포·secret을 변경하지 않고 설계 초안을 작성했다.
`docs/superpowers/specs/2026-10-30-real-ai-enrichment-design.md`에 총예산,
중복 검사 순서, 원문 보존, 비동기 요약, 비용 원장, 공개 provenance와 검증 기준을 기록했다.
STATUS·ROADMAP 양언어에는 계획과 구현을 구분하고 제품 우선순위를 반영했다.

### 설계 고민과 트레이드오프

- 현재 소스에서 enrichment가 중복 검사보다 먼저 실행되는 점을 재확인했다.
  실제 provider로 교체하기 전에 이 경계를 바꿔야 반복 수집의 유료 중복 호출을 피할 수 있다.
- 월별 예산 대신 누적 예산을 택하고 앱 한도 4달러·여유 1달러를 제안했다.
  첫 버전은 호출별 0.02달러를 보수적으로 차감하고 실제 추정액과 분리한다.
  미확정 요청을 자동 재전송하지 않는 정책은 일부 처리량보다 비용 보존을 우선한다.
- 공식 모델 문서에서 GPT-5.6 Luna의 요금과 structured output 지원을 확인해 첫 후보로
  기록했다. 계정 접근 가능성·키·잔액·한국어 생성 품질은 확인한 사실이 아니다.
- 자가 검토에서 FastAPI 별도 DB 원장 제안을 제거했다. Spring의 PostgreSQL 원장과
  양쪽 HTTP retry 비활성·미확정 요청 격리로 책임을 유지하는 작은 구조를 택했다.
- 첫 pilot은 최대 10회 시도이며 mock 전체 backfill, 전문 수집 확대, 상시 호스팅은
  분리했다. 이 문서 검토와 실행 계획·구현·실제 호출은 남은 작업이다.
