# 2026-10-30 개발 로그: 실제 접속 복구와 단일 서버 배포 준비

## 요약

오래 중지된 Sigak 서비스를 다시 시작하고 오늘 기준 전체 검사를 실행했다.
이전 개발 내용이 로컬에만 남아 있음을 확인하고 GitHub와의 차이를 구분했다.

## 설계 고민 / 결정

정적 Sites-only 배포는 기존 JVM backend를 실행할 수 없으므로 실제 기사 검색 서비스의 대체가 되지 않는다. 기존 Spring Boot public boundary와 PostgreSQL 원본을 유지하고 한 서버의 Compose에 Caddy만 공개하기로 했다.

SPA는 알 수 없는 경로에도 index.html을 반환하므로 API 제한이 fallback보다 먼저 실행돼야 한다. 정확한 공개 API와 GET/HEAD만 proxy하고 내부·unknown API에는 404, API 쓰기 method에는 405를 반환한다. 실제 HTTP 검사에서 이 경계를 확인했다.

기존 개발 DB와 새 배포 DB를 분리했다. 배포 설정 실험이 수집 기사 41개를 덮어쓰지 않도록 새 DB는 샘플 5개로 검증하고 기존 데이터는 보존했다. 연구 artifact의 catalog 41개는 API가 읽는 보존 artifact의 크기이며 새 배포 DB의 기사 수와 구분한다.

## 트레이드오프

- 서버 한 대로 운영 구성을 단순화했지만 HA나 자동 backup/scheduler는 포함하지 않는다.
- 임시 HTTPS 공유는 검증했지만 서버나 도메인이 없어 상시 인터넷 서비스와 사용자 도메인 TLS는 미검증이다. 유료 자원 생성이나 결제는 하지 않았다.
- JDK Alpine tag의 ARM manifest 부재를 실제 빌드에서 확인해 Jammy 기반으로 교체했다. 이미지 크기보다 현재 ARM/향후 서버 호환성을 우선했다.
- Host의 기존 node_modules로는 발견되지 않던 peer lock 누락을 Linux clean install로 찾았다. 설치 우회 대신 lock을 보완하고 같은 빌드를 다시 실행했다.
- 평가 테스트의 초기 19개 실패는 sandbox DNS/tokenizer 다운로드 문제였다. 네트워크 허용 후 같은 70개가 통과했으며 코드 오류로 기록하지 않는다.
- Dataset 사람 검토는 여전히 0개다. 생성·judge·전체 품질 평가 gate를 변경하지 않았다.

## 후속 작업: Sigak 기술 뉴스 정기 수집

### 사용자 선택과 구현 범위

사용자는 news-rag의 경향신문 수집 데이터를 옮기는 대신 Sigak의 기술 뉴스 source를 자동 실행하도록 선택했다. 별도 news-rag 컨테이너·코드·데이터는 변경하지 않았다. 기존 개발 DB 41개는 실제 수집 36개와 seed 5개였고, 마지막 실제 수집은 한국시간 6월5일이었다는 DB 감사도 수행했다. 기존 news-rag worker의 600초 반복·최근 성공은 별도로 확인했으며 두 프로젝트를 혼동해 보고하지 않도록 구분했다.

구현 파일: collection config의 `CollectionAutomationProperties/Config`, service의 `CollectionAutomationService`, dto의 `CollectionAutomationStatus`, runner의 `CollectionAutomationScheduledJob`, controller의 `CollectionAutomationController`, 관련 automation test3개 파일. `application.yml`, root/deployment env example, deployment Compose와 backend Dockerfile, 내부 API 계약·배포 안내·상태/로드맵을 갱신했다.

### 이유와 트레이드오프

- 별도 scheduler나 Airflow를 새로 도입하지 않고 기존 Spring backend에 opt-in fixed-delay job을 연결했다. 개발/test는 꺼 두고 배포만 기본 활성화한다.
- 완료 후 대기와 in-process guard로 예약 실행 중복을 막는다. 한 backend만 지원하며 replica 간 분산 잠금과 수동 작업 동시 실행은 지원하지 않는다.
- 신규 저장 뒤 projection이 실패해도 PostgreSQL은 보존한다. 다음 실행이나 재시작에서 새 기사가 없어도 복구한다. 수집 도중 일부가 저장된 뒤 예외가 난 경우도 pending으로 남기는 회귀 테스트를 RED→GREEN으로 검증했다.
- 각 저장소 갱신 실패를 격리하고 정제된 오류 타입만 남긴다. `lastSuccessfulAt`와 `lastPublishedAt`를 구분해 일부 실패를 성공처럼 보고하지 않는다.
- 진단 snapshot은 메모리 상태이고 재시작 시 초기화된다. 실제 기사/실패 이벤트/volume cooldown만 영속적이다. 전체 run history나 가동률 계산은 구현하지 않았다.
- 기존 mock enrichment와 bounded feed batch, 전체 projection rebuild를 유지한다. 유료 LLM, 과거 전체 backfill, 대규모 증분 색인은 추가하지 않았다.

- 브라우저에서 신규 OpenAI 기사(한국시간10월30일 발행)의 실제 제목·날짜·원문 링크·요약 표시를 확인했다. 화면을 `outputs/deployment-2026-10-30/automatic-news-article.jpg`에 보존했다. 요약/why-it-matters는 기존 mock 결과이며 외부 유료 생성 품질을 검증한 것이 아니다.

## 후속 설계: 누적 5달러 이내 실제 AI 기사 요약

### 요약과 완료한 일

사용자가 실제 AI 요약을 요청하고 기존 OpenAI 잔액 약 5달러 이내 사용을 선택했다.
이번 후속 세션에서는 코드·배포·secret을 변경하지 않고 설계 초안을 작성했다.
`docs/superpowers/specs/2026-10-30-real-ai-enrichment-design.md`에 총예산,
중복 검사 순서, 원문 보존, 비동기 요약, 비용 원장, 공개 provenance와 검증 기준을 기록했다.
STATUS·ROADMAP 양언어에는 계획과 구현을 구분하고 제품 우선순위를 반영했다.

### 설계 고민과 트레이드오프

- 현재 소스에서 enrichment가 중복 검사보다 먼저 실행되는 점을 재확인했다.
  실제 provider로 교체하기 전에 이 경계를 바꿔야 반복 수집의 유료 중복 호출을 피할 수 있다.
- 월별 예산 대신 누적 예산을 택하고 앱 한도 4달러·여유 1달러를 제안했다.
  첫 버전은 호출별 0.02달러를 보수적으로 차감하고 실제 추정액과 분리한다.
  미확정 요청을 자동 재전송하지 않는 정책은 일부 처리량보다 비용 보존을 우선한다.
- 공식 모델 문서에서 GPT-5.6 Luna의 요금과 structured output 지원을 확인해 첫 후보로
  기록했다. 계정 접근 가능성·키·잔액·한국어 생성 품질은 확인한 사실이 아니다.
- 자가 검토에서 FastAPI 별도 DB 원장 제안을 제거했다. Spring의 PostgreSQL 원장과
  양쪽 HTTP retry 비활성·미확정 요청 격리로 책임을 유지하는 작은 구조를 택했다.
- 첫 pilot은 최대 10회 시도이며 mock 전체 backfill, 전문 수집 확대, 상시 호스팅은
  분리했다. 이 문서 검토와 실행 계획·구현·실제 호출은 남은 작업이다.

### 다음 단계와 주제 후보

작성한 설계를 사용자와 검토한 뒤 실행 계획·구현으로 전환한다. 키는 서버 환경에만
설정하고 유료 pilot 이전에 예산·중복·재시작·timeout 정책을 테스트한다.
대안 비교, 실패 복구, 비용 경계, MVP 이후로 미룬 범위 조건에 해당해 topic-queue에
“작은 유료 AI 예산에서 중복 호출과 미확정 비용을 다루는 설계”를 설계 단계 후보로 추가했다.
후보에는 실제 운영 검증 근거가 아직 없음을 명시했다.

### 사용자 검토 반영: 클릭한 기사만 요약

사용자가 읽히지 않는 기사에 미리 비용을 쓰지 말고 클릭 시 요약을 제안했다.
같은 설계 초안을 첫 상세 진입 시 생성·방문자 간 저장 결과 공유로 수정했다.
수집·목록·검색과 유료 생성을 분리하고, 요약 없는 기사의 공개·검색을 지원하는 것으로
범위를 바꿨다. 자동 선생성·신규 수집 시 작업 등록·기존 mock 전체 backfill은 제외했다.
더 절약하는 대안으로 상세의 명시적 요약 버튼도 비교해 두었다.

추가 소스 확인에서 repository가 current enrichment를 inner join하고, article mapper가
current enrichment 없으면 오류를 발생시키며, frontend schema는 summary를 필수 문자열로
요구하는 것을 확인했다. 따라서 nullable DTO·상태 표시뿐 아니라 공개 조회·검색/graph
reader 계약도 함께 바꿔야 한다. Caddy는 모든 공개 write를 차단하므로 새 summary POST만
정확히 허용하는 변경과 실제 HTTP 검증이 필요하다.

읽기 GET은 유료 호출 없이 유지하고, 실제 상세 진입 이후 POST로 작업을 요청하도록
제안했다. 동시 방문은 같은 작업을 공유하고 새로고침·polling이 추가 호출을 만들지 않는다.
첫 방문자는 요약 영역에서 기다리되 제목·소개글·원문 링크는 바로 본다. 이번 반영도
문서 변경만이며 코드·실제 요약 지연·유료 사용량은 미검증이다.

수정 후 Python으로 선생성 정책 잔존 여부, 요청 시 생성·GET 무과금·동시 요청 단일화
계약, 문서 링크 네 개를 검사해 PASS를 확인했고 `git diff --check`도 성공했다.
이는 설계 문서의 일관성 확인이며 실제 동작 테스트 결과가 아니다.

## 후속 구현: 첫 상세 방문 시 실제 AI 요약

### 요약과 완료한 일

사용자가 상세 진입 시 비동기로 요약하고 저장 결과를 재사용하는 구현을 승인했다.
수집은 AI 호출 없이 원문부터 공개하고, 상세의 별도 POST가 공유 요약 작업을 요청하도록
바꿨다. 실제 OpenAI 요약2건과 저장 결과 재사용·재시작 보존을 확인했다.
최종 외부 출처 설정·이미지 검증은 아래 마무리 기록에서 구분한다.

주요 파일은 `backend/.../article/summary/`의 계약·작업 원장·서비스·HTTP client·controller,
`V4__on_demand_summaries.sql`, article repository/service/DTO와 수집 persistence,
검색 projection/vector builder, `ai/app/services/openai_enrichment_service.py`,
`frontend/src/components/ArticleSummary.tsx`, `frontend/src/api/summaries.ts`, Compose/Caddy다.
작업 계획은 `docs/superpowers/plans/2026-10-30-real-ai-enrichment.md`에 보존했다.

### 설계 결정과 트레이드오프

- 요약 없는 기사도 `PUBLISHED`이면 공개한다. current enrichment inner join을 제거하고
  DTO의 요약/중요성 설명을 nullable로 바꿨다. 기존 mock은 실제 AI 요약으로 노출하지 않는다.
- Spring의 짧은 DB transaction에서 기사 행 잠금으로 요청을 합치고, 별도 worker가
  영속 budget row와 pending job을 잠가 비용 예약·DISPATCHED 전환을 함께 완료한다.
  외부 HTTP는 transaction 밖에서 실행한다. 별도 broker/Celery/FastAPI DB는 도입하지 않았다.
- 유료 경계는 private FastAPI의 고정 `gpt-5.6-luna` Responses 호출이다. 전체 전송16KiB,
  출력2048token, 구조화된 schema, 근거 문자열·한국어·사용량 검증을 적용했다.
  모델 도구·SDK 숨은 재시도는 사용하지 않는다. 개발 mock JSON 계약은 그대로 유지한다.
- 누적5달러 승인 중 앱은4달러, 총200회·일20회에서 멈추고 호출마다0.02달러를 보수적으로
  차감한다. 실제 token 추정액과 예약 차감액은 다르다. UNKNOWN은 환급하거나 자동 재요청하지
  않는다. 인증·모델·사용량·결제 실패는 원장의 circuit을 멈춘다.
- 기본 pilot은 최대10회다. 운영 전환 시 자동 승인 검토가 “소수 시험에서200회로 확대”라는
  이유로 한 번 거절했다. 현재 한도를 우회하지 않고 사용자에게 이유를 설명했고,
  사용자가 “운영 모드 전환 허용 — 총5달러 이내”를 명시적으로 승인했다.
- 첫 방문의 기다림을 수용해 안 읽히는 기사의 비용을 없앴다. 제목·출처 소개글·원문 링크는
  먼저 보이고 요약 영역만 생성 중이다. 완료 결과와 근거를 공유하고 상태 GET만 polling한다.
- 방문 여부가 검색에 영향을 주지 않도록 keyword/vector/fallback 모두 수집 텍스트를 쓴다.
  AI 중요도 제안은 기존 공개 점수를 자동 변경하지 않는다. 신규 점수는50이다.
- 사용자가 키 발급도 요청해 로그인된 Chrome에서 별도 restricted Responses-write 키를
  발급했다. 만료일2026-11-29이며 비공개 배포 env에만 저장했다. 채팅·Git·로그에 키 값을
  출력하지 않았고 기존 news-rag 키를 재사용하지 않았다. 계정 잔액·자동 충전은 미검증이다.

### 실패에서 확인한 경계

- 기존 publication 테스트를 바꾸자 실제로 enrichment 호출과 summary 없는 article 제외가
  RED로 나타났다. 이를 바꾼 뒤 원문 우선 공개와 요청 시 생성으로 연결했다.
- 임의 Mockito matcher의 Kotlin null 검사 실패는 테스트 helper로 수정했다.
  요약 worker 테스트의 article fixture가 다음 suite에 남는 문제는 AfterEach에서 제거했다.
- 기본 vector builder 테스트가 옛 summary 입력을 기대해 실패했다. sourceExcerpt로 바꾸고
  생성 요약이 달라져도 embedding 입력이 같음을 검사했다.
- 독립 검토에서 유료 AI가 개발 Compose의 공개8000포트로 우회될 수 있음을 지적해
  localhost bind로 제한했다. 배포 AI는 원래부터 host port가 없다.
- 사용량 초과·결제429를 일반502로 숨기면 Spring circuit이 멈추지 않는 점을 수정했다.
  AI fixture에서 실제 RED→GREEN을 확인했다. 단순 rate limit과 결제 오류를 구분한다.
- 응답 유실 뒤 JDK client가 POST를 반복하지 않는 것을 실제 로컬 HTTP server로 검사했다.
  JVM 연결 재시도도 끄고 Spring 대기75초를 AI 내부45초보다 길게 잡았다.
- 실제 생성문에 입력 범위 enum이 포함돼 화면에서 자연스러운 한국어로 표시하도록
  별도 UI 회귀 테스트를 RED→GREEN으로 검증했다. 저장 원문·근거 인용은 바꾸지 않았다.
- 기존 임시 주소는 DNS 실패, 다른 Cloudflare DNS는 정상, 터널은 Unauthorized/Tunnel not
  found였다. 새 임시 주소를 발급했다. 새 외부 조회 검사는 통과했지만 Origin을 포함한 POST는
  Invalid CORS request403이었다. 외부 HTTPS→내부 HTTP 차이를 재현하고 정확한 public origin
  한 개만 허용했다. 설정 class의 Kotlin 기본 생성자가 @Value 주입을 건너뛰는 문제도
  javap으로 확인해 제거했다. 와일드카드 허용·전달 헤더 무조건 신뢰는 도입하지 않았다.

## 후속 세션: 소개글 대신 본문 전체로 요약하고 대기를 줄이기

### 요약 / 완료한 일

일반 기사 우선 설계를 사용자가 승인했다. 본문은 무료로 미리 준비하고 유료 요약은 상세
첫 방문 때만 생성한다. Spring의 V5/article_full_texts와 fulltext/ 경로, 기존 summary/ 경로를
연결했으며 수집 소개글은 검색용으로 별도 보존했다. 기존 원장·요약 이력은 초기화하지 않았다.
관련 spec/plan은 `docs/superpowers/`의 `2026-10-30-fulltext-summary-latency*`다.

AI는 FULL_TEXT/v2 입력을 자르지 않고 실제 전송64KiB를 검증한다. Spring은 중첩 JSON56KiB
사전 제한으로 고정8KiB를 남긴다. 현재 provider 고정 포장은2176bytes였다. HTTP 연결은
FastAPI 수명 동안 재사용하고, 저장된 작업은 즉시 단일 실행기를 깨우며2초 복구 확인을 남겼다.
화면은500ms 확인·본문 준비/요약 생성 구분·본문 기반 근거 표시를 제공한다.

### 설계 결정 / 트레이드오프

읽히지 않는 기사에 AI를 쓰지 않으면서 대기를 줄이기 위해 본문 준비만 선행했다.
스트리밍·전체 과거 기사 재처리·arXiv 전문은 미뤘다. GPT prompt 캐시 쓰기를 켜는 대신
완성된 결과를 DB에서 공유한다. 전문을 앞부분으로 자르거나 수집 실패를 소개글로 숨기지 않는다.
본문 저장 직후 종료돼도 requested_summary를 확인해 유료 예약 누락을 복구한다.

실제 HTML로 확인하니 OpenAI 추천 카드, Google 공유/추천 영역, GitHub 저자/태그가 섞였다.
출처별 실제 본문 컨테이너로 좁히고 결론·코드·노이즈 제거 테스트를 추가했다.
첫 GitHub 실수집에서는 공개192.0.66.2를 예약192.0/16로 과도하게 차단했다.
허용/차단 회귀 테스트 RED를 본 뒤192.0.0/24·192.0.2/24 등 정확한 범위로 좁혀 고쳤다.
해당 무료 작업만 수동1회 재개했고 금전 원장·UNKNOWN 작업은 건드리지 않았다.
