# 2026-05-05 개발 로그: Sigak MVP 기반 설계와 첫 구현

## 요약

오늘은 Sigak의 방향을 정리하고, 문서화 중심의 초기 설계에서 실제로 동작하는 첫 MVP 흐름까지 연결했다. 이어서 프론트엔드 디자인도 Bloomberg/Financial Times 스타일로 리디자인해 Article detail 페이지까지 완성했고, 마지막으로 Phase 4 프론트엔드 MVP foundation의 남은 상태 처리와 문서 정합성까지 마무리했다.

Sigak은 단순한 뉴스 요약 앱이 아니라 AI, 개발, CS 분야의 중요한 기술 변화를 선별하고, 왜 중요한지와 어떤 개념과 연결되는지를 보여주는 기술 뉴스 인사이트 플랫폼으로 정의했다. 이 방향에 맞춰 문서, 백엔드, 프론트엔드의 첫 구조를 만들었고, 이후 프론트엔드를 의도적으로 설계된 시각 언어로 다듬었다.

## 오늘 완료한 일

### 1. 제품 방향 정리

처음에는 "AI-powered news insight platform"이라는 넓은 표현에서 시작했지만, 범위를 더 구체화했다.

Sigak의 초기 타깃은 AI, 소프트웨어 개발, 컴퓨터공학 분야에 관심 있는 사람이다. 특히 다음과 같은 정보가 중요하다고 판단했다.

- 주요 AI/CS 연구 발표
- 심각한 보안 이슈
- 공식 기업/기관 발표
- 중요한 오픈소스 릴리즈
- 개발자 생태계에 영향을 줄 수 있는 기술 변화

반대로 일반적인 개인 기술 블로그, 튜토리얼, 홍보성 콘텐츠, 낮은 영향도의 패치 릴리즈는 초기 수집 대상에서 제외하기로 했다. MVP 단계에서는 신뢰할 수 있는 source와 선별 기준이 더 중요하다고 봤기 때문이다.

### 2. Graph RAG 방향 결정

Graph RAG는 Sigak의 장기적인 차별점이 될 수 있지만, 처음부터 Obsidian 같은 전체 그래프 탐색 UI를 만드는 것은 비용이 크다고 판단했다.

그래서 1.0.0에서는 다음 수준까지만 포함하는 방향으로 정리했다.

- 기사 데이터에 관계형 메타데이터를 포함한다.
- `relatedArticleIds`, `topics`, `primaryCategory`처럼 나중에 Graph RAG로 확장 가능한 필드를 둔다.
- 제한적인 관계 기반 인사이트는 준비한다.
- full graph explorer는 MVP 이후로 미룬다.

이 결정 덕분에 지금 당장 복잡한 그래프 UI에 시간을 쓰기보다, 검색, 요약, 중요도, 관계형 메타데이터라는 핵심 기반을 먼저 만들 수 있게 됐다.

### 3. 문서화

프로젝트의 기준 문서를 먼저 정리했다.

- `AGENTS.md`: 프로젝트 규칙, 기술 스택, 개발 방식, 테스트 규칙, 블로그 작성 규칙
- `docs/PROJECT_CONTEXT.md`: 제품 맥락과 MVP 목표
- `docs/PRODUCT_PLAN.md`: 제품 기획, source 정책, Graph RAG 전략
- `docs/ROADMAP.md`: 단계별 개발 순서
- `docs/API_SPEC.md`: 현재 API 계약과 필드 설명
- `docs/SOURCE_POLICY.md`: 포함/제외할 뉴스 source 정책
- `docs/decisions/0001-initial-architecture.md`: 초기 아키텍처 ADR
- `docs/decisions/0002-product-scope-and-graph-rag-strategy.md`: 제품 범위와 Graph RAG 전략 ADR

문서를 먼저 작성한 이유는 이후 구현이 흔들리지 않도록 하기 위해서다. 특히 Article 모델의 필드나 API 응답 구조는 제품 방향과 직접 연결되기 때문에, 코드보다 먼저 기준을 잡는 편이 좋다고 판단했다.

### 4. Monorepo 구조 생성

초기 monorepo 구조를 만들었다.

```txt
sigak/
├── backend/
├── frontend/
├── ai/
├── infra/
└── docs/
```

각 영역의 책임도 나눴다.

- `backend`: Spring Boot 메인 API 서버
- `frontend`: React + TypeScript + Vite UI
- `ai`: FastAPI 기반 AI/RAG 기능 영역
- `infra`: Docker Compose와 로컬 개발 인프라
- `docs`: 제품, API, 아키텍처 문서

Spring Boot가 메인 API boundary이고, FastAPI는 AI/RAG 기능에만 사용하는 구조로 정했다. 프론트엔드는 기본적으로 Spring Boot만 호출한다.

### 5. Kotlin Spring Boot 백엔드 구현

백엔드는 Kotlin Spring Boot로 세팅했다. 이전 Java 코드와 관련 테스트는 제거하고 Kotlin 기준으로 정리했다.

현재 제공하는 API는 다음과 같다.

```http
GET /api/articles
GET /api/articles?query={query}
GET /api/articles/{id}
```

아직 DB, Elasticsearch, Qdrant는 붙이지 않았다. 대신 mock data로 Article API의 모양을 먼저 검증했다.

Article 응답에는 다음 필드를 포함했다.

- `id`
- `title`
- `source`
- `url`
- `publishedAt`
- `eventType`
- `primaryCategory`
- `topics`
- `summary`
- `whyItMatters`
- `importanceScore`
- `relatedArticleIds`

중요한 점은 `summary`만 있는 뉴스 카드가 아니라, `whyItMatters`, `importanceScore`, `topics`, `relatedArticleIds`를 포함해 나중에 관계형 인사이트로 확장할 수 있게 만들었다는 것이다.

### 6. 검색 API 구현

첫 검색 기능은 매우 작게 시작했다.

```http
GET /api/articles?query=rag
```

검색 대상은 다음으로 제한했다.

- title
- summary
- primaryCategory
- topics

대소문자와 앞뒤 공백은 무시한다. 지금은 in-memory mock data를 필터링하지만, API 응답 형태를 안정적으로 유지하면 나중에 Elasticsearch나 semantic search로 내부 구현을 바꿔도 프론트엔드 계약은 크게 흔들리지 않는다.

### 7. Swagger/OpenAPI 추가

API도 문서화가 필요하다고 판단해서 `springdoc-openapi`와 Swagger UI를 추가했다.

로컬 실행 후 다음 경로에서 확인할 수 있다.

```txt
http://localhost:8080/swagger-ui/index.html
http://localhost:8080/v3/api-docs
```

Spring REST Docs도 고려했지만 지금 단계에서는 도입 비용이 더 크다고 판단했다. 그래서 Swagger/OpenAPI는 실행 가능한 API 문서로 사용하고, `docs/API_SPEC.md`는 사람이 읽는 설계 문서로 유지하기로 했다.

### 8. React + TypeScript + Vite 프론트엔드 구현

프론트엔드는 Vite 기반으로 세팅했고, 첫 화면은 검색 중심으로 만들었다.

구성은 단순하다.

- 중앙 검색바
- Today 기사 목록
- Popular News 기사 목록
- 기사 카드

프론트엔드 API 호출은 직접 `fetch`를 흩뿌리지 않고 `src/api/` 아래로 분리했다.

HTTP 요청에는 Axios를 사용했고, 백엔드 응답 검증에는 Zod를 사용했다.

```txt
frontend/src/api/httpClient.ts
frontend/src/api/articles.ts
```

Zod를 둔 이유는 TypeScript 타입만으로는 런타임 API 응답을 보장할 수 없기 때문이다. 백엔드 응답이 문서와 달라졌을 때 UI 컴포넌트까지 잘못된 데이터가 들어가기 전에 API client boundary에서 실패하게 만드는 것이 더 안전하다고 봤다.

### 9. CORS 설정 (PR #1)

프론트엔드 Vite dev server에서 백엔드 API를 호출할 수 있도록 Spring Boot에 CORS 설정을 추가했다.

허용 origin은 로컬 개발에 필요한 두 가지로 제한했다.

```txt
http://localhost:5173
http://127.0.0.1:5173
```

처음에는 `localhost`만 허용했지만, Vite가 `127.0.0.1` 주소를 안내하는 경우가 있어서 실제 curl 확인 중 403이 발생했다. 이 문제를 확인한 뒤 테스트와 설정을 함께 보강했다.

### 10. 프론트엔드 디자인 리디자인 (PR #2)

초기 MVP 구조가 잡힌 뒤, 프론트엔드의 시각 디자인을 의도적으로 설계된 방향으로 재정비했다. Bloomberg, Financial Times 같은 전문적이고 미니멀한 저널리즘 스타일을 기반으로, serif 타이포그래피와 인디고 악센트 컬러 시스템을 도입했다.

#### 디자인 시스템

CSS Custom Properties(design token)로 전체 색상과 폰트 체계를 한 곳에 정의했다.

- **serif 폰트(Georgia)**: 기사 제목과 본문 — 신뢰감과 읽기 편안함
- **sans-serif(-apple-system)**: UI 크롬(라벨, 메타, 태그) — 현대적이고 기능적
- **인디고 악센트**: `#4F46E5` (링크, 태그, 강조 요소)

`importanceScore`는 UI에 노출하지 않기로 결정했다. 큐레이션 품질 자체가 신뢰감을 주는 것이 목표이기 때문이다. 대신 내부적으로 Popular News 상위 3개 선별에는 사용한다.

#### 구현한 컴포넌트

**NavBar**: 로고(Georgia serif) + `AI · Security · Engineering` 힌트. detail 페이지에서는 `← Back to News` 링크로 교체.

**ArticleListItem**: 기사 제목(Georgia) + 카테고리 태그(인디고 배경) + 출처·날짜(우측 정렬 그레이). 클릭 시 `/articles/{id}`로 이동.

**HomePage**: 검색바(둥근, 연한 인디고 배경) → Today's Important News → Popular News(importanceScore 상위 3개). 검색 시 `SEARCH RESULTS FOR "query"` 헤더로 교체. 두 섹션 간 기사 중복 없음.

**ArticleDetailPage**: 카테고리 태그 + 이벤트 타입 태그 → 제목(24px Georgia) → 바이라인(출처·날짜·원문 링크) → SUMMARY → WHY IT MATTERS(인디고 왼쪽 보더 박스) → TOPICS 칩 → RELATED ARTICLES 리스트.

#### React Router 도입

`react-router-dom` v7을 추가하고 클라이언트 사이드 라우팅을 구성했다.

```txt
/              → HomePage
/articles/:id  → ArticleDetailPage
```

`fetchArticle(id)` API 함수도 추가해 detail 페이지에서 개별 기사를 불러올 수 있게 했다. related articles는 `Promise.all`로 병렬 패칭한다.

### 11. Phase 4 마무리와 상태 처리 개선

프론트엔드 MVP foundation을 닫기 전에, 화면이 정상 데이터만 있을 때가 아니라 로딩, 빈 데이터, 실패 상황에서도 자연스럽게 동작하는지 점검했다.

개선한 내용은 다음과 같다.

- 홈 화면 로딩 문구를 `Loading articles...`로 구체화했다.
- 홈 feed가 비어 있을 때 Today's Important News와 Popular News 섹션을 각각 비우는 대신 하나의 빈 상태 메시지(`No articles available yet.`)만 보여주도록 했다.
- 홈 feed 로드 실패 시 `Retry` 버튼을 제공해 사용자가 새로고침 없이 다시 요청할 수 있게 했다.
- Article detail 로딩 문구를 `Loading article...`로 구체화했다.
- Article detail 로드 실패 시 접근 가능한 `alert` 상태와 `Back to home` 링크를 제공했다.
- ROADMAP을 체크박스 기반으로 정리하고, Phase 4의 남은 항목을 현재 구현 상태에 맞춰 모두 체크했다.
- `README.md`, `frontend/README.md`, `PRODUCT_PLAN.md`, `API_SPEC.md`에서 article detail 구현 상태와 `importanceScore` 표시 정책을 맞췄다.

이 작업에서 중요한 결정은 `importanceScore`를 detail 화면에 숫자로 보여주지 않는 것이다. 점수는 정렬과 큐레이션을 위한 내부 신호로 유지하고, 사용자가 보는 화면에서는 `whyItMatters`가 중요성을 설명하게 했다. 현재 seed data가 manually curated mock data라는 점을 고려하면, 88/100 같은 숫자를 노출하는 것보다 이유 중심의 설명이 더 정직하고 신뢰를 준다고 판단했다.

## 주요 결정과 트레이드오프

### DB보다 mock API를 먼저 선택

초기부터 DB를 붙이면 구조는 그럴듯해 보일 수 있지만, 제품의 핵심 흐름이 아직 충분히 검증되지 않은 상태에서는 비용이 크다. 그래서 지금은 mock data로 API 계약, 검색 흐름, 프론트 연동을 먼저 검증했다.

DB는 mock data가 한계를 보일 때 붙이는 것이 맞다고 판단했다.

### Elasticsearch와 Qdrant는 보류

검색과 Graph RAG를 생각하면 Elasticsearch와 Qdrant가 자연스럽게 떠오르지만, 지금은 너무 이른 단계다.

현재 목표는 검색 API의 사용자 경험과 응답 구조를 안정화하는 것이다. 내부 구현은 나중에 바꿀 수 있도록 두고, 지금은 in-memory keyword search로 충분하다고 봤다.

### Swagger는 도입, Spring REST Docs는 보류

API 문서화는 바로 필요했다. 프론트엔드와 백엔드 계약을 확인하기 위해서다.

다만 Spring REST Docs는 테스트 기반 문서화라는 장점이 있지만 초기 설정과 유지 비용이 있다. MVP 단계에서는 `springdoc-openapi`가 더 가볍고 빠르게 가치를 줄 수 있다고 판단했다.

### Axios와 Zod 사용

프론트엔드 API 호출은 Axios로 통일했다. 동시에 Zod를 사용해 API 응답을 런타임에서 검증했다.

이 조합은 작은 프로젝트에서는 약간의 추가 작업처럼 보일 수 있지만, API 계약이 자주 바뀌는 초기 MVP에서는 오히려 문제를 빨리 발견하게 해준다.

### importanceScore를 UI에서 숨기는 결정

`importanceScore`(0-100)는 백엔드에 존재하지만 UI에는 노출하지 않기로 했다. 숫자를 보여주면 오히려 신뢰감을 해칠 수 있고, 큐레이션 자체의 품질이 신뢰를 만들어야 한다고 판단했다.

점수는 Popular News 섹션의 상위 3개 선별에만 내부적으로 사용하고, 화면에는 나타나지 않는다.

### CSS Design Token 전략

전역 CSS Custom Properties로 색상과 폰트를 한 곳에 정의하고, 모든 컴포넌트 스타일에서 token을 참조하게 했다. 나중에 다크 모드나 테마 변경이 필요할 때 token 값만 바꾸면 전체에 적용된다.

### 상태 화면은 작은 기능이지만 MVP 신뢰도를 만든다

로딩, 빈 결과, 실패 상태는 기능 목록에서는 작아 보이지만 실제 사용자가 MVP를 만졌을 때 완성도를 크게 좌우한다. 특히 포트폴리오 프로젝트에서는 정상 흐름만 보이는 것보다 실패했을 때 어떻게 회복할 수 있는지가 더 좋은 엔지니어링 판단을 보여준다고 봤다.

그래서 복잡한 UI를 추가하기보다, 현재 흐름에 꼭 필요한 최소 상태만 보강했다. 홈 feed 실패에는 `Retry`, detail 실패에는 `Back to home`을 둔 것도 같은 이유다.

## 실행 방법

백엔드:

```bash
cd backend
./gradlew bootRun
```

프론트엔드:

```bash
cd frontend
npm run dev
```

접속 주소:

```txt
Frontend: http://localhost:5173
Backend API: http://localhost:8080/api/articles
Swagger: http://localhost:8080/swagger-ui/index.html
```

## 다음 할 일

프론트엔드 기본 흐름(홈 → 검색 → detail 페이지)과 Phase 4 상태 처리는 마무리됐다. 다음 단계는 데이터와 AI 레이어를 실제로 붙이는 것이다.

- **PostgreSQL 연결**: 현재 in-memory mock data를 DB로 교체하고 JPA persistence를 붙인다.

오늘 작업의 핵심은 화려한 기능을 많이 만든 것이 아니라, 제품 방향과 기술 구조, 그리고 시각적 디자인이 모두 같은 방향을 보도록 맞춘 것이다. 이제부터는 이 기반 위에서 실제 데이터 레이어를 하나씩 붙이면 된다.
