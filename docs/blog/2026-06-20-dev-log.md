# 2026-06-20 개발 로그: 운영 문서 RAG 평가 하네스 설계

## 요약

NAVER 인턴의 RAG 평가 과제와 Sigak의 현재 구현을 다시 대조했다.
짧은 article summary catalog에 chunking 실험을 붙이는 대신, README, API spec,
demo flow, fallback 기록을 운영 매뉴얼 corpus로 사용하는 방향을 선택했다.
이번 세션에서는 구현하지 않고 corpus, evaluation dataset, chunking, retrieval,
reranking, generation, LLM judge, human calibration의 계약을 spec으로 고정한 뒤,
이를 12개 TDD task와 세 개 실행 checkpoint로 나눈 구현 계획까지 작성했다.

## 설계 고민 / 결정

현재 41개 article catalog는 검색 시스템 비교에는 유용하지만 title, summary,
why-it-matters 중심이라 chunking 효과를 보여주기 어렵다. 지원 과제의 키워드를
맞추기 위해 형식적인 chunking 실험을 추가하면 오히려 평가 신뢰도가 낮아진다.

그래서 실제 heading, 명령어, API 계약, 장애 대응 절차가 있는 Sigak 운영 문서를
versioned corpus로 선택했다. 정답도 chunk ID에 직접 묶지 않고 document path,
heading path, quote hash로 관리한다. 이 방식이면 chunking 전략이 바뀌어도 같은
근거를 기준으로 비교할 수 있다.

LLM judge는 자동 평가 수단으로 사용하지만 ground truth로 간주하지 않는다.
두 chunking strategy의 generation 차이도 확인하기 위해 다섯 generation variant를
실행하고 최소 50개 답변을 사람이 검토하도록 보강했다.

계획 단계에서도 “코드부터 만들고 query를 나중에 맞추는” 순서를 피했다. 24개
information need의 lexical/semantic pair와 12개 unanswerable query 내용을 먼저
고정하고, dataset-freeze commit 이후 retrieval 결과를 보도록 checkpoint를 나눴다.
또한 OpenAI key가 없는 deterministic baseline은 BM25/dense/hybrid 6개 조합까지만
완료로 보고, reranking을 포함한 8개 factorial matrix는 full run에서만 완료로
판정하도록 분리했다.

운영 문서는 Qdrant, fallback, endpoint처럼 exact keyword가 많은 corpus다. 질문도
같은 표현을 반복하면 BM25가 구조적으로 유리해진다. 반대로 dense의 장점을
보여주겠다는 이유로 keyword를 부자연스럽게 제거한 질문만 만들면 dense에 유리한
평가셋이 된다. 따라서 같은 information need에 lexical query와 자연스러운 semantic
paraphrase를 하나씩 두고, 두 행을 하나의 intent cluster로 해석하기로 했다.

## 트레이드오프

얻은 것:

- 운영 매뉴얼형 RAG 과제와 직접 연결되는 공개 corpus
- 기존 article search를 변경하지 않는 독립 실험 경계
- retrieval과 generation 실패를 분리하는 평가 구조
- 자기소개서 완료형 주장과 artifact를 연결하는 evidence contract

미룬 것:

- public chatbot API와 frontend
- 외부 로봇 PDF manual parsing
- chunk-level Elasticsearch/Qdrant projection
- coding-agent benchmark와 Kubernetes anomaly detection
- research dashboard 구현
