# 2026-06-05 개발 로그: arXiv 검증과 확장 검색 카탈로그 준비

## 요약

오늘은 두 갈래 작업을 진행했다.
먼저 GitHub issue #14를 닫기 위해 arXiv cooldown 이후 원래 5-source collection runtime smoke를 단일 실행했고, 결과를 issue comment로 남긴 뒤 close했다.
이어서 기존 6개 article smoke catalog를 덮어쓰지 않고, 현재 PostgreSQL의 API-ready article을 `api-ready-2026-06-05` 계열 frozen catalog로 export했다.

검색 품질을 바로 주장하지는 않았다.
41개 article catalog는 다음 라벨링과 expanded benchmark를 위한 기준점이고, 기존 `api-ready-2026-06-02` smoke baseline은 그대로 보존한다.

## 설계 고민 / 결정

#14를 닫는 검증에서는 코드를 더 고치지 않았다.
2026-06-03 세션에서 반복 smoke가 오히려 arXiv quota를 자극했기 때문에, #14 close 검증은 cooldown 후 단일 runtime smoke로 제한했다.
반복 `bootRun`은 매번 새 JVM을 만들기 때문에, 메모리 timestamp만으로는 이전 run의 arXiv 요청 시각을 알 수 없다.
그래서 마지막 arXiv 요청 시작 시각을 configurable local file에 저장하고, file lock으로 같은 머신의 짧은 반복 실행을 조율하도록 했다.

검색 catalog는 기존 `articles.catalog.json`을 덮어쓰지 않았다.
label과 result artifact가 특정 `catalogId`와 article ID 집합을 전제로 하기 때문이다.
6개 article smoke 결과는 runner가 end-to-end로 동작했다는 재현성 baseline이고, 41개 article catalog는 다음 평가를 위한 새 기준점이다.
따라서 새 catalog, 새 label, 새 result는 `api-ready-2026-06-05` 계열 이름으로 분리한다.

## 트레이드오프

- 얻은 것: 실제 arXiv export API를 포함한 5-source collection-run이 `COMPLETED`로 끝난 증거를 얻었다.
- 얻은 것: 반복 command-run cooldown을 실제 arXiv 호출 없이 deterministic test로 검증할 수 있게 됐다.
- 얻은 것: 현재 DB 상태를 기준으로 41개 API-ready article catalog를 확보해 10-15개 query label 작성 기반을 만들었다.
- 미룬 것: 여러 머신에서 동시에 arXiv를 호출하는 distributed cooldown guard는 아직 없다.
- 미룬 것: 새 label JSON 작성, retrieval benchmark 재실행, graph-aware evaluation 재실행은 사용자의 수동 라벨링 이후로 남겼다.
- 주의점: article 수가 늘었다고 검색 품질이 좋아졌다고 말할 수는 없다.
